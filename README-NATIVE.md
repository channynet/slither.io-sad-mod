# Slither Native + NTL 시험판

Windows용 Vlither 2.6 기반 개인 사용 시험판입니다. 게임 화면과 조작은 네이티브 Vulkan 클라이언트에서 처리하며 NTL 팀 통신은 별도 작업 스레드에서 처리합니다.

## 2.6-ntl0.102 — IP 기반 상세 지역 정보

관리자 화면은 Cloudflare가 제공하는 추정 국가·시도·도시·우편번호·위도·경도·시간대·통신망 운영기관을 표시합니다.
이 값은 IP 주소에 연결된 추정 정보입니다. 실제 집이나 건물의 위치를 보장하지 않습니다.
기기의 위치 측정값은 수집하지 않습니다. 별도 유료 조회 서비스는 사용하지 않습니다.
제공되지 않은 값은 미확인으로 표시합니다. 기존 기록의 상세 정보는 다음 게임 접속 확인 때 갱신됩니다.
기존 접속 기록과 차단 목록은 유지합니다. 시작 화면 하단의 수집 안내 문구는 제거했습니다.
수집 항목과 보관 기간은 배포본의 README-KO.txt와 관리 서버 README에 기재합니다.

## 2.6-ntl0.101 — 클라이언트 접속 관리

게임 접속 시 관리 서버가 접속 IP 주소·추정 국가·도시·앱 버전·최근 접속 시각을 기록합니다.
접속 기록의 기본 보관 기간은 30일입니다. 시작 화면에 수집 안내를 표시합니다.
관리자는 `클라이언트 관리.cmd`로 관리자 화면을 열어 접속 현황을 확인하고 IP 주소를 차단하거나 해제합니다.
클라이언트는 게임 접속 전에 차단 여부를 확인합니다. 게임 중에는 60초마다 확인합니다.
관리 서버 장애 시에는 게임 접속을 허용합니다. 구버전과 수정된 앱에는 사용 제한을 강제할 수 없습니다.
자세한 설정과 저장 범위는 `tools/tag-share-worker/README.md`를 확인하세요.

## 2.6-ntl0.99 — 실시간 서버 선택

1. 시작 화면의 **Play 바로 위에 있는 실시간 서버 선택**을 누릅니다.
2. 목록에서 국가·지역, 서버 주소, 접속 수, 핑, 정보 갱신 시각을 확인합니다.
3. 서버를 선택하면 아래에 상위 10명의 닉네임과 점수가 표시됩니다.
4. **선택한 서버로 접속**을 누릅니다.

목록은 창을 연 동안 30초마다 갱신합니다. 주소·국가·도시 검색과 접속 수·핑·국가 정렬을 지원합니다.
공개 목록의 출처는 https://leaderboard.0x0efe.dev/ (saya)입니다. NTL의 화면 구성을 참고했으며 NTL 서버의 데이터를 사용하는 기능은 아닙니다.
접속 수에는 봇이 포함될 수 있습니다. 지역은 제공자의 국가·시간대 정보입니다. 핑은 내 PC에서 보이는 서버의 `/ptc` 응답을 측정한 값이며 실제 게임 핑과 다를 수 있습니다.
수신에 실패하면 이전 목록과 실패 상태를 함께 표시합니다. 5분이 지난 서버 정보에는 오래된 정보라는 표시가 붙습니다. 기존 주소 직접 입력과 최근 서버 목록은 계속 사용할 수 있습니다.
목록을 받기 위한 별도 지렁이는 생성하지 않습니다. 창을 닫으면 새로운 목록 요청을 중단합니다.

## 2.6-ntl0.98 — 미사일 기능 분리 보관

현재 앱과 배포본에서 미사일 생성, G 단축키, 미사일 설정, 목표 표시와 미사일 엔진을 제거했습니다.
미사일 기능은 `archive/snake-missile-0.97` 브랜치의 커밋 `99d4d1e`에 보관했습니다.
이 브랜치에는 엔진 원본, 통합 코드, 검사와 빌드 도구가 모두 있습니다.
복원할 때는 보관 브랜치와 현재 코드의 차이를 검토해 필요한 부분만 이식합니다.
앱은 미사일 엔진이 없어도 정상 실행되며 엔진을 다시 설치하지 않습니다.
Windows 업데이트는 남아 있는 구버전 엔진을 `.update/retired`에 보관합니다.

## Windows 자동 업데이트

Windows의 `SlitherNative.exe`는 실행할 때 `channynet/slither.io-sad-mod`의 최신 정식 GitHub Release를 확인합니다. 새 버전이 있으면 실행 파일과 기본 리소스를 함께 설치합니다. 설치가 끝나면 앱이 자동으로 실행됩니다. 게임 도중에는 업데이트를 적용하지 않습니다. 인터넷 연결이나 업데이트 확인이 실패하면 기존 버전으로 실행됩니다. 최초 확인은 최대 8초이며, 새 배포본 다운로드가 필요하면 실행까지 시간이 더 걸릴 수 있습니다.

업데이트는 GitHub가 제공한 SHA-256 해시와 파일 크기를 검증합니다. 교체 전 파일은 `.update/backup`에 보관됩니다. 파일 교체가 실패하면 기존 파일을 복구합니다. 중단된 교체는 다음 실행에서 복구합니다. 사용자 설정·팀 키·개인 이미지는 배포 파일에 포함하지 않습니다. 업데이트 결과는 `.update/status.txt`에 기록됩니다. `update.ps1`은 실행 파일과 같은 폴더에 있어야 합니다. 이름이 다른 개발용 실행 파일과 macOS 앱은 이 Windows 업데이트를 실행하지 않습니다.

배포 절차:

1. 개발자는 `tools/build_windows.py`의 버전을 올립니다.
2. 개발자는 해당 버전의 코드와 `v2.6-ntl0.98` 형식의 태그를 GitHub에 푸시합니다.
3. GitHub Actions는 Windows 검사와 배포 파일 생성을 수행합니다.
4. GitHub Actions는 검사가 통과한 배포본을 정식 Release에 게시합니다.
5. 사용자의 앱은 다음 실행에서 새 버전을 자동으로 설치합니다.

업데이트 회귀 검사는 `powershell -NoProfile -ExecutionPolicy Bypass -File tests/update_test.ps1`로 실행합니다. 실제 프로세스 교체·재시작 검사는 `python tools/test_auto_update.py`로 실행합니다. 두 검사는 격리된 임시 폴더를 사용합니다.

## 2.6-ntl0.90 — 방향 지정 돌진과 빌드 통합

0.83~0.89의 태그 공유·태그 설정·팀 닉네임·맥 시작 수정을 포함합니다. GitHub Actions는 main 푸시와 main 대상 병합 요청에서 맥 앱을 빌드합니다. 자동 검사는 창 모드와 전체 화면의 앱 시작을 확인합니다.

네트워크 검사는 TCP 왕복 지연 통계의 미지원 상태도 검증합니다. 이 상태에서도 수신 순서, 데이터 내용, 처리 반복 상한과 연결 종료 검사는 실행됩니다. 운영체제 일정에 따라 달라지는 처리 호출 횟수는 측정값으로 출력합니다.

당시 추가한 Q/G 조작과 이후 미사일 기능은 현재 배포본에서 제거했습니다.

## 실행

`dist/SlitherNative.exe`를 실행합니다. `app` 폴더가 실행 파일 옆에 있어야 합니다. 실행 파일만 따로 옮기지 마세요.

1. 가운데 메뉴에서 닉네임과 게임 서버의 `IP:포트`를 입력합니다. 기존 NTL에서 사용하는 서버 주소를 그대로 사용할 수 있습니다.
2. **F8**로 왼쪽 아래 팀 채팅을 열고 **설정**에서 인증키와 팀 ID를 입력합니다. **팀키 저장**을 누르면 연결하지 않고도 두 키를 현재 Windows 계정으로 암호화해 보관합니다. **팀 연결**을 누를 때도 자동 저장합니다. 다음 실행에는 자동으로 불러오므로 **팀 연결**만 누르면 됩니다.
3. **NTL 연결 확인**은 서버 응답에 자신의 접속이 포함됐다는 뜻입니다. 단순히 응답이 왔다는 것과 구분합니다.
4. **Play**로 입장하면 자신의 게임 좌표와 점수가 약 4초 간격으로 팀 서버에 전달됩니다. 죽거나 메뉴로 돌아오면 메뉴 상태로 전환됩니다.
5. 채팅은 아래 입력란에서 Enter 또는 **전송**으로 보냅니다. 실제 전송은 다음 팀 갱신 때 이뤄집니다.

팀 창은 **H 두 번** 또는 **F8**로 숨기거나 다시 열 수 있습니다. **F11**은 전체 화면입니다. 기본 게임 조작은 마우스 방향 이동, 왼쪽 클릭·Space·Shift·위쪽 화살표 가속, 휠 확대/축소입니다. 채팅 입력 중에는 게임 단축키와 가속 입력을 막습니다.

## 타겟과 사망 장면 정지 (0.11)

- **Backspace 두 번** 또는 게임 중 팀 채팅의 **설정 → 타겟 선택**으로 화면 안 상대 머리 위에 선택 문자를 표시합니다. 해당 **0~9 / A~Z**를 누르면 상대에게 빨강·흰색 과녁이 붙습니다. 선택 중 **Esc**는 취소, **Delete**는 표적 해제이며 같은 상대를 다시 선택해도 해제됩니다. 선택 문자는 선택 창을 여는 동안 고정되어 상대가 움직이거나 추가되어도 다른 상대와 바뀌지 않습니다.
- 이 버전의 타겟은 내 화면에 표시하는 기능입니다. NTL 팀의 TMS 공유 송수신이나 봇 추적은 추가하지 않았습니다. 최신 팀 정보로 확인할 수 있는 팀원과 자신은 선택 대상에서 제외합니다. 상대가 클라이언트의 수신 범위를 벗어나거나 죽으면 표적을 해제합니다. 재접속 시에도 해제하며 같은 서버 ID가 다른 지렁이에 재사용되어도 이어 붙이지 않습니다.
- **사망 순간 화면 정지**는 기본으로 켜집니다. 서버에서 내 사망을 알리면 마지막으로 그린 게임 장면을 그대로 유지합니다. 기존 자동 재시작보다 우선하며 **R / 다시 시작**으로 같은 서버 재입장, **Esc / 메뉴로**로 빠져나옵니다. 설정 창 또는 **Ctrl+F4**로 켜고 끌 수 있으며 재실행해도 설정이 유지됩니다.
- 이 화면은 클라이언트의 마지막 게임 장면이며 서버의 정확한 충돌 좌표·판정을 재현하는 리플레이는 아닙니다. 별도 녹화·매 프레임 이미지 복사 없이 기존 그래픽 메모리의 화면 한 장을 유지합니다. 정지 중 창 크기가 바뀌어도 원래 화면 비율을 유지합니다.

## 팀 채팅과 기존 미니맵 통합 (0.9)

- 왼쪽 아래 반투명 채팅 창에 수신 시각·닉네임·본문을 표시합니다. **Enter**로 입력하고 Enter 또는 전송 버튼으로 전송합니다. **Esc**는 입력을 끝내고 게임으로 돌아갑니다. 위로 스크롤해 과거 메시지를 읽는 중에는 새 메시지가 와도 맨 아래로 이동하지 않습니다.
- **설정**에서 팀 연결·저장 키 관리·이미지 태그·cosmetic·성능 옵션을 조절합니다. 채팅 창에는 별도 팀 지도를 표시하지 않습니다.
- 같은 서버의 팀원은 오른쪽 아래 기존 미니맵에 초록 점, SOS는 빨간 점과 테두리로 표시합니다. 마우스를 올리면 이름·점수·마지막 응답 경과 시간을 볼 수 있습니다. 자신의 기존 위치 표시를 중복하지 않습니다.
- 미니맵 좌표는 현재 경기장 중심과 반경, 지도 크기와 내부 여백을 반영합니다. 다른 서버·메뉴 상태·잘못된 좌표·경기장 밖 위치·10초 넘게 갱신되지 않은 응답은 숨깁니다. 서버를 바꾸면 새 서버에서 받은 응답이 확인될 때까지 이전 팀 위치를 표시하지 않습니다.
- 채팅 숨김과 **V V**의 통계 숨김은 독립적이며 팀 위치는 기존 지도에 유지됩니다. 숨긴 통계를 채팅 Enter 입력 때문에 다시 켜지 않습니다.
- 팀 통신의 정상 갱신 주기는 기존 약 4초입니다. 점은 마지막 수신 위치이며 실시간 이동을 보장하지 않습니다. 추가 서버 요청이나 게임 지도 텍스처 업로드 없이 점만 덧그립니다.
- **오프라인 화면 시험**은 실제 메시지를 보내지 않고 시험 채팅과 초록/SOS 위치를 확인합니다. 지도 시험 위치는 활성화 시점의 경기장 기준이므로 게임 접속 후 시험을 켭니다.

## 최근 서버 주소 (0.8)

주소 입력칸 오른쪽 화살표에서 최근 서버 주소를 선택합니다. **Play**로 접속을 시도한 유효한 `IPv4:포트` 주소를 최근 순서로 20개까지 기억하며, 같은 주소는 중복하지 않고 앞으로 옮깁니다. 목록 선택만으로 접속하지 않으며 **Play**를 눌러야 합니다. 처음 업데이트할 때 기존에 저장돼 있던 마지막 주소를 가져오고, 이후 목록은 `server-history.txt`에 보관해 재실행 후에도 유지합니다. 과거에 저장되지 않은 전체 방문 기록을 복원하는 기능은 아닙니다.

주소가 바뀌어 목록 순서가 달라질 때만 저장하며, 동일 서버 자동 재접속이나 게임 프레임마다 기록하지 않습니다. 잘못된 형식은 목록에 넣지 않으며 저장에 실패하면 메뉴에 알립니다. 팀키 저장과는 별개입니다.

## 복잡한 봇 기능과 일반 플레이 성능

현재 호출 경로는 `game_loop → oef → [봇 켜짐 && 내 지렁이 플레이 중] → sbot_go`입니다. 봇을 끄면 충돌점 수집/정렬, 먹이 탐색, 감기 경로 계산은 호출되지 않습니다. 입력 전송도 봇이 켜졌을 때만 봇 방향·가속 결과를 사용합니다. 시작할 때 고정 크기 봇 상태를 한 번 초기화하며, 현재 봇 전용 작업 스레드나 별도 타이머는 없습니다.

따라서 새 기능의 계산을 이 활성 조건 안에만 넣으면 일반 플레이 중 그 계산 비용이 추가되지는 않습니다. 반대로 꺼진 상태에서도 매 프레임 주변 상황을 미리 분석하거나, 백그라운드 계산을 계속하거나, 큰 모델/캐시를 항상 유지하면 CPU·GPU·메모리 경쟁으로 일반 플레이도 영향을 받을 수 있습니다.

현재 봇 계산은 화면 처리와 같은 스레드에서 실행됩니다. 켠 상태에서 계산이 길어지면 프레임과 입력 처리가 밀릴 수 있으므로, 복잡한 기능은 활성화 시 필요한 자원만 준비하고, 꺼지면 작업을 중단하며, 계산 빈도/대상 수/시간 예산을 제한해야 합니다. 무거운 계산을 별도 작업으로 분리할 때도 게임 스레드가 결과를 기다리지 않게 하고, 비활성 상태에서는 작업을 멈춰야 합니다. 아직 요청되지 않은 복잡한 봇 기능이나 실행 구조 변경은 추가하지 않았으며, 미래 기능의 영향은 실제 구현 후 봇 꺼짐/켜짐을 각각 측정해야 합니다.

## 단축키 (0.4)

NTL 9.68의 기본 키를 기준으로 이미 구현된 기능만 연결했습니다. **두 번**은 다른 키를 사이에 누르지 않고 1초 안에 같은 키를 두 번 누르는 방식입니다. 키를 누른 채로 유지해도 두 번 누른 것으로 처리하지 않습니다.

| K 두 번 | 보조 화면 모드 고정 전환; R을 눌렀다 떼면 해제 |

## 성능 설정

0.5에서는 화면 중간이 가로로 어긋나는 화면 찢어짐을 막도록, 즉시 화면 교체(IMMEDIATE)를 사용하지 않습니다. 기본은 지원되는 장치에서 MAILBOX, 지원하지 않으면 FIFO를 선택합니다. **Strict VSync**를 켜면 FIFO를 사용합니다. 두 방식 모두 화면 찢어짐을 허용하지 않으며, **F8** 창에서 적용된 표시 방식을 확인할 수 있습니다. 화면 표시 속도는 모니터 주사율의 제한을 받습니다.

사용하지 않는 4096×3548 배경 텍스처와 밉맵(픽셀 데이터 약 73.9MiB)을 1픽셀 텍스처로 대체했습니다. 회색 격자 모습은 유지합니다. 미니맵이 숨겨지면 그리기·전송을 생략하고, 보일 때도 해당 프레임 버퍼의 내용이 바뀐 경우에만 전송합니다. 게임 장면을 완성한 뒤 화면 합성에서 읽도록 GPU 동기화를 명시했으며, 화면 크기 변경 중 이미지 획득이 실패하면 다음 프레임을 무한 대기할 수 있던 fence 초기화 순서도 수정했습니다. 창 크기 변경 콜백 안에서 즉시 렌더링하지 않고 전환이 끝난 다음 재구성하며, 별도 크기 변경 이벤트 없이도 표시 버퍼를 복구합니다. 전체 화면 전환으로 버퍼 수가 바뀌면 표시 완료 동기화 객체도 다시 만듭니다.

추가 최적화 후보는 혼잡 서버에서 지렁이 몸통과 먹이의 화면 밖 계산을 더 줄이는 것, 미니맵 보간을 변경된 영역만 처리하는 것, 프레임 제한 대기 중 CPU 사용을 줄이는 것입니다. 이 항목들은 아직 적용하지 않았으며 같은 서버·줌·해상도에서 측정한 뒤 결정해야 합니다. 게임 서버의 핑 변동은 렌더링 최적화와 별개입니다.

- 기본: **60 FPS**, 게임 해상도 **75%**, 그림자·먹이 흔들림·광원 등 추가 효과 최소화, 회색 격자 배경.
- 글자와 팀 창은 전체 해상도로 그리며, 게임 장면만 선택한 해상도로 그립니다.
- 75% 설정은 가로·세로를 각각 75%로 줄입니다. 게임 장면 픽셀 수는 100%의 약 56%입니다. 성능 향상률을 의미하지는 않습니다.
- 그래픽 설정에서 효과를 다시 켤 수 있습니다. 팀 창의 **가벼운 그래픽 적용**으로 가벼운 설정을 다시 적용합니다.
- FPS는 최근 최대 600프레임의 평균 간격에서 계산합니다. **느린 1%**는 같은 구간의 프레임 간격 99백분위 값입니다. **33ms 초과**는 그 구간의 긴 프레임 개수입니다.
- **핑**은 게임 서버 통신 지연입니다. NTL 팀 갱신 간격과는 다릅니다. 멀리 있는 서버의 핑은 렌더링 최적화로 낮출 수 없습니다. 게임 메뉴에서는 핑이 0으로 표시됩니다.

FPS 제한·게임 해상도·전체 화면·팀 창 표시 상태는 `native-settings.json`, 창 배치는 `native-layout.ini`, 일반 그래픽·닉네임·서버·스킨·단축키 설정은 `user.dat`에 저장됩니다. 설정 변경을 약 0.75초 간격으로 감지해 저장하며 정상 종료 때도 저장합니다. 재실행할 때 가벼운 그래픽 값을 덮어쓰지 않습니다. 봇 작동·누르고 있는 보조키·재시작 명령은 실행 중 상태이므로 자동으로 다시 켜지지 않습니다.

팀 인증키와 팀 ID는 Windows DPAPI로 암호화해 `%LOCALAPPDATA%\SlitherNative\team-keys.dat`에 별도 저장합니다. 자동으로 팀에 접속하지는 않습니다. 팀 창의 **저장된 팀키 삭제**로 다음 실행 시 불러오기를 해제할 수 있으며, 이미 연결된 세션은 **연결 해제**를 누를 때까지 유지됩니다.

## 내 머리에 매다는 이미지 태그

1. **Skin editor → 태그 / cosmetic → 태그** 또는 팀 채팅의 **설정 → 이미지 태그 / cosmetic → 내 이미지 태그**에서 **이미지 추가/바꾸기**를 누릅니다.
2. 원하는 **PNG/JPG/BMP** 파일을 선택합니다. 투명 PNG도 지원합니다. 파일은 최대 16MB, 가로·세로 각각 4096px까지 받습니다.
3. **크기**, **연결 줄 길이**, **회전 보정**을 조절합니다. 이미지 비율은 유지됩니다. **Ctrl+F8** 또는 **태그 표시**로 켜고 끕니다.

살아 있는 내 지렁이의 머리에 연결해 표시하며, 다른 사람에게 이미지를 전송하지 않습니다. 선택한 이미지는 긴 변 최대 512px로 줄여 `personal-tag.rgba`에 보관하고 표시 여부·크기·간격은 `personal-tag.json`에 저장합니다. 원본 파일을 옮겨도 다음 실행에 복원됩니다. 이미지 파일 선택은 게임 메뉴에서만 가능하며 플레이 중에는 크기·간격·표시 여부를 바꿀 수 있습니다.

0.1에서 처음 업데이트할 때만 NTL 기본 단축키와 회색 격자 배경을 적용하고 기존 닉네임·서버·스킨·나머지 그래픽 설정은 유지합니다. 이후 사용자가 바꾼 값은 그대로 불러옵니다.

## 내 이미지 cosmetic (0.4)

**Skin editor → 내 cosmetic** 또는 **F8 → 내 cosmetic**에서 원하는 PNG/JPG/BMP를 선택합니다. 태그와 별개의 이미지를 사용할 수 있습니다. 기본 예시로 투명 배경의 검은 깃털 날개를 포함했으며, **검은 날개 예시** 버튼으로 다시 선택할 수 있습니다. 이미지 파일 선택은 게임에 들어가기 전에 합니다.

- 태그는 머리에 연결된 줄 끝을 따라 움직이고 cosmetic은 머리 근처에 붙어 지렁이 크기·방향·줌을 따라갑니다.
- 크기·앞뒤 위치·방향 회전 여부·회전 보정을 조절할 수 있습니다. 이미지의 위쪽을 지렁이의 앞 방향으로 사용합니다.
- 스킨 편집 화면에서 장착 모습을 미리 볼 수 있습니다. 기존 기본 장식과 함께 표시할 수 있습니다.
- **Ctrl+F8**은 태그, **Ctrl+F9**는 cosmetic을 각각 켜고 끕니다. 둘 다 내 화면에만 보이고 서버에 전송하지 않습니다.
- cosmetic 이미지와 설정은 `personal-cosmetic.rgba` 및 `personal-cosmetic.json`에 저장됩니다. 기존 태그 저장은 유지합니다.
- 이미지가 없는 슬롯에는 처음 실행할 때 검은 날개 예시를 준비합니다. 이미 선택한 이미지와 표시 설정은 덮어쓰지 않습니다.
- 예시 원본은 `app/res/personal/black-wings.png`이며 내장 이미지 생성 도구로 제작했습니다. 사용한 전체 프롬프트는 같은 폴더의 `BLACK-WINGS.txt`에 있습니다.

## 끊김과 조작 지연 수정 (0.7)

한산한 곳에서도 끊겼다는 사용자 보고를 바탕으로 입력·통신과 화면 표시 대기의 연결을 수정했습니다. 당시의 성능 기록은 없어 그 사건의 단일 원인은 확정하지 않았습니다.

- 기존 방향/키보드/가속 전송 간격 50/150/150ms를 33/50/50ms로 줄였습니다. 이는 [NTL 공식 변경 기록](https://ntl-slither.com/slither/)의 9.55 명시 값입니다. 이후 9.58에도 타이밍 로직 수정이 기록되어 있으므로 최신 NTL과 모든 동작이 같거나 실제 반응 시간이 같다는 뜻은 아닙니다.
- 화면 획득·GPU 완료를 한 번에 오래 기다리던 부분을 1ms 단위로 반환하도록 변경했습니다. 프레임 제한 대기 중에도 짧은 간격으로 최신 마우스 입력과 게임 통신을 처리합니다. 같은 스레드에서 수행하므로 별도 스레드가 게임 상태를 동시에 수정하지 않습니다. 드라이버의 화면 제출 자체나 크기 변경 작업까지 무조건 1ms 안에 끝난다는 보장은 아닙니다.
- 한 번의 서버 수신 처리 뒤에도 데이터가 남으면 최대 8회/소프트 예산 2ms까지 추가 처리합니다. 수신 버퍼는 64KiB로 미리 준비합니다. Windows의 기존 수신 버퍼 증가 단위는 16KiB였습니다. 이는 인터넷 왕복 시간을 줄이는 기능이 아니라 클라이언트 안에서 쌓인 데이터를 빨리 처리하는 수정입니다.
- 0.6의 FIFO 최소 이미지 수 정책을 되돌려 최소+1개를 요청합니다(장치 상한 적용). [Khronos 설명](https://docs.vulkan.org/samples/latest/samples/performance/swapchain_images/README.html)처럼 2개 버퍼는 화면 표시 시점을 놓쳤을 때 프레임 속도가 크게 떨어질 수 있습니다. 실제 지연과 안정성의 균형은 장치별로 다르며 화면 찢어짐 방지 정책은 유지합니다.
- 외곽선은 몸통 내부까지 덧칠하던 작업을 생략하고 얇은 테두리 부분만 처리합니다. GPU 대기 중 들어온 단축키는 다음 그리기까지 보존합니다.
- 서버 응답을 프레임 사이에 받더라도 현재 시각을 기준으로 핑을 계산합니다.

`dist/performance.csv`에는 약 1초마다 평균/최대 프레임 시간, 33ms 초과 횟수, 화면 대기·통신·이동 계산·그리기 준비·제출·프레임 제한 시간, 수신량, 남은 수신량, 그리기 수, 표시 모드/버퍼 수, 마지막/구간 최대 핑을 기록합니다. 마지막 핑은 새 응답이 없으면 유지되며 구간 최대 핑 0은 새 측정이 없었다는 뜻입니다. 메뉴·크기 변경도 프레임 간격에 포함되므로 재현 당시 상황과 함께 해석해야 합니다. 시간 항목은 CPU에서 측정한 값이며 GPU 실행 시간이나 실제 입력부터 화면 표시까지의 지연을 직접 측정하지 않습니다.

기록 쓰기는 별도 스레드에서 수행하고, 게임 쪽은 기록 잠금을 기다리지 않습니다. 현재 기록과 이전 기록(`performance.previous.csv`) 두 파일만 유지하며, 재실행 또는 약 3,600개 기록마다 교체합니다. 팀키·채팅·닉네임·서버 주소는 기록하지 않습니다.

개선 연구: 회전 가능한 경로를 비교하는 [Dynamic Window Approach](https://publications.ri.cmu.edu/the-dynamic-window-approach-to-collision-avoidance)의 원리를 참고해 이 게임의 멈출 수 없는 이동에 맞게 구현했습니다. 로봇 실험의 안전 보장을 게임에 그대로 적용하지 않습니다. 사용자가 제공한 sliterapp ZIP의 급회전 반복 사망 기록은 방향 유지 설계의 참고 자료로만 사용했으며 코드/학습 모델은 복사하지 않았습니다.

다음 검증 우선순위는 (1) 사망 직전의 익명 좌표/명령 기록으로 회전·지연 모델 보정, (2) 포위되기 전 넓은 탈출 통로를 찾는 장기 탐색, (3) 여러 서버에서 기존 봇과 번갈아 반복해 생존 시간 중앙값·10분당 사망·판단 시간 p95 비교입니다. 단일 경기나 녹화 재생만으로 생존율 향상을 주장하지 않습니다.

실서버 작동 확인(0.12): 약 74.7초, 봇 평균 0.079ms/프레임, 전체 평균 56.1FPS, 33.3ms 초과 145프레임/4,193프레임. 검사 종료로 연결을 닫았으며 생존율 비교 실험은 아닙니다. 화면 대기/제출에서 끊김이 남아 있어 렌더링 성능 개선과 봇 생존 검증을 별도로 진행해야 합니다.

## 0.13 봇 직진 고정 및 조작 차단 수정

- 방향 유지 벌점이 먹이 접근 보상보다 커서 안전한 공간에서는 직진만 선택하던 문제를 수정했습니다. 작은 회전에 대한 벌점을 완화하고, 먹이 방향과 이전 목표 방향을 후보에 추가합니다(최대 19개). 안전한 경로 우선 규칙은 유지합니다.
- 봇 ON일 때 채팅 입력/팀 패널 위 마우스/게임 창 포커스 상실이 자동 방향 전송을 막지 않도록 수정했습니다. 수동 조작의 입력 차단 및 봇 부스트 OFF는 유지합니다.
- 기존 `T` 두 번으로 활성화/비활성화합니다. 시작 시에는 OFF이고, 채팅 입력 중 단축키는 작동하지 않습니다. 채팅 입력을 마친 뒤 게임 화면에서 누르세요.
- 회귀 검사: 좌우 먹이로 회전, 작은 각도의 먹이로 회전, 위험 경로 거부, 실제 방향 전송 함수의 채팅/마우스 포획/포커스 분기. 수정 전 두 핵심 검사의 실패를 확인했고 수정 후 전체 오프라인 검사가 통과했습니다. 이번 수정의 실서버 생존율은 아직 측정하지 않았습니다.

## 0.14 수동 회전 이어받기

- 회전 중 `T`를 두 번 눌러 봇을 켜면 최근 수동 회전의 방향과 대략적인 반지름을 이어받아 계속 돕니다. 직진 중 켜면 기존 수비형으로 동작합니다. 별도 전략 UI/단축키는 추가하지 않습니다.
- 최소 약 0.08초의 회전 기록을 사용하며, 짧게 회전이 끊긴 프레임도 허용합니다. 봇 OFF에서는 자기 머리 방향만 관찰하고 경로 탐색은 하지 않습니다.
- 원을 도는 경로 전체의 충돌 위험과 맵 경계를 검사합니다. 위험하면 수비 회피를 우선하고 해당 원을 따라갈 수 있으면 복귀합니다. 먹이는 회전 유지보다 우선하지 않습니다.
- 끄고 다시 켜면 그때의 수동 움직임을 새로 읽습니다. 사망/새 지렁이 생성 시 이전 회전 상태를 초기화합니다. 회전 반지름은 추정치이고 실제 회전 한계·지연·위험 회피 때문에 처음과 완전히 같지는 않을 수 있습니다.
- 자동 검사: 양쪽 방향으로 여러 바퀴 유지, 반지름 범위, OFF/ON 초기화, 먹이보다 회전 우선, 위험 및 경계 회피, 위험 제거 후 회전 복귀. 실서버에서 장시간 유지 성능은 미측정입니다.

### Assist 확장 검토 (미구현)

현재 Assist는 R을 누르는 동안, 또는 K 두 번으로 고정한 동안 방향선과 별도 그래픽 설정을 표시합니다. 아래는 추가 후보이며 조작에 개입하는 기능을 이번 변경에서 자동으로 활성화하지 않습니다.

1. **짧은 예상 경로**: 마우스까지의 직선 대신 현재 속도·회전 한계·입력 지연을 반영한 0.3~0.6초 경로를 표시합니다. 지렁이의 회전 반경을 판단하는 데 도움을 줄 수 있습니다. 자신의 상태만으로 계산할 수 있어 가장 가벼운 후보입니다.
2. **근접 충돌 경고**: 위 경로와 가까운 상대 몸통/머리·맵 경계가 겹치면 표시를 노랑/빨강으로 바꿉니다. 기존 defensive_planner의 단일 경로 평가를 재사용할 수 있습니다. 전체 17~19개 후보 탐색 대신 현재 진행 경로 하나만 평가하되, 장면 수집 비용까지 같은 비율로 줄어드는 것은 아닙니다.
3. **핑 변동 경고**: 평균 핑뿐 아니라 최근 지연 변동·응답 공백을 반영해 예상 경로를 흐리게 하고 여유 거리를 늘립니다. 네트워크 지연을 없애는 기능이 아니라 예측의 불확실성을 드러내는 기능입니다.
4. **표적 접근 보조**: 선택한 상대의 머리 방향과 짧은 예상 이동만 표시합니다. 상대가 갑자기 회전할 수 있으므로 확정적인 공격 성공 표시로 사용하지 않습니다. 현재 화면에 수신된 정보만 사용합니다.
5. **수동 조작 보호 보조**: 위험할 때 부스트 해제/작은 방향 보정을 할 수 있지만, 의도적인 근접 조작을 방해할 수 있어 우선순위는 낮습니다. 도입한다면 별도 동의·설정 및 누르는 동안만 작동하는 방식이 적절합니다.

구현 우선순위는 예상 경로 → 충돌 경고 → 핑 변동 반영입니다. 계산은 Assist가 꺼지면 중단하고, 경로/경고 계산은 10~15Hz로 제한하며 화면에서는 결과만 그립니다. 봇과 Assist가 동시에 켜지면 이미 만든 주변 장면을 공유하도록 설계합니다. 성능 목표는 혼잡한 장면의 계산 시간과 p99 프레임 간격으로 검증해야 하며, 아직 실행 시간이나 생존율 개선을 측정한 것은 아닙니다. 표시되는 경로·위험 범위는 추정치이며 서버의 정확한 충돌 판정이 아닙니다.


## 0.17 이름 단일 색과 NTL 팀원 색

- 팀 채팅의 설정 → **이름 색상**에서 **이름 단일 색**을 켜면 일반 플레이어 이름을 기본 색으로 통일하고, 같은 서버의 NTL 팀원 이름 전체만 지정한 팀원 색으로 표시합니다. 기본은 켜짐이며 Ctrl+F11로 전환합니다.
- 팀원 판별은 기존 타겟 기능과 동일한 NTL 식별자를 사용합니다. 닉네임 태그나 문자열 일치로 판별하지 않습니다. 팀 연결이 없거나 정보가 10초 이상 오래됐거나 서버가 다르면 기본 이름 색으로 표시합니다.
- 점수는 팀원 여부와 관계없이 기본 색입니다. 단일 색을 끄면 기존 스킨 기반 이름/점수 색으로 돌아갑니다. 게임 내 이름의 글자·배치·외곽선과 NTL 전송 내용은 유지합니다.
- 0.16의 팀 표기 입력 및 부분 문자열 강조는 제거했습니다. 이전에 고른 팀원 색은 유지하고 사용하지 않는 팀 표기 설정은 무시합니다. 단일 색 상태·기본 색·팀원 색은 재실행 후에도 유지됩니다.
- 화면에 보이는 이름에만 기존 NTL 팀원 조회를 적용합니다. 별도 통신이나 경로 탐색은 추가하지 않습니다. Assist 확장 검토안은 위와 같으며 아직 미구현입니다.


## 0.18 머리에 매다는 태그

- NTL 공식 태그 안내(https://ntl-slither.com/uploadtag.php)의 줄 연결 방식과 이미지 부착점을 참고해 독립 구현했습니다. 화면 위 고정 배지 방식을 제거하고 머리에서 시작하는 짧은 줄과 회전을 따라가는 태그로 변경했습니다. NTL의 정확한 물리 시뮬레이션이나 태그 공유 프로토콜을 복제한 것은 아닙니다.
- 일반 이미지는 위쪽 중앙에 줄을 연결하고 뒤로 매달립니다. 지렁이 크기와 줌에 맞춰 줄과 이미지가 함께 확대/축소됩니다. 방향 전환 시 약 0.09초의 회전 추종을 사용하며 프레임률에 독립적입니다. 회전 보정은 이미지의 연결점을 중심으로 적용합니다.
- 기존 이미지·크기·표시 설정은 유지합니다. 이전 버전의 화면 위 간격은 새 연결 줄 길이 24로 한 번 이관하고 회전 보정은 0으로 시작합니다. 이미지 파일과 cosmetic 설정은 그대로 유지합니다. 새 태그 설정은 버전 2로 저장됩니다.
- 매 프레임 고정된 6개 선분과 이미지 사각형 하나만 계산합니다. 이미지 재업로드/파일 읽기/네트워크 요청을 프레임마다 추가하지 않습니다. 태그를 끄거나 죽거나 재접속하면 이전 회전 기록을 초기화합니다.
- 자동 검사: 머리 연결점, 양 방향 회전, 이미지 비율, 줌, 부착점 기준 회전, 60/120FPS 추종 일치, 사망 후 새 개체·시간 초기화·일시 중지 복귀.
- 태그/cosmetic 이미지가 게임 화면보다 먼저 배경 목록에 그려져 가려질 수 있던 순서도 수정했습니다. 게임 위, 설정 창 아래에 표시합니다.
- 검증: 전체 자동 검사·Windows 빌드 통과. 기존 태그 파일의 버전 1→2 이관과 cosmetic 설정 보존, 실서버에서 머리에 연결된 검은 날개 태그 표시 확인. 테스트 후 표시 여부는 기존 꺼짐 상태로 복원했습니다.


## 0.19 스킨 설정에서 태그 편집

- **Skin editor** 오른쪽의 **태그 / cosmetic** 창에 태그 탭을 추가했습니다. 태그 이미지 선택·검은 날개 예시·표시 전환·크기·연결 줄 길이·회전 보정을 여기서 편집할 수 있습니다.
- 스킨 미리보기의 머리에 같은 태그를 붙여 즉시 확인합니다. 게임과 동일한 그리기 함수를 사용하며, 편집 미리보기는 게임 중 회전 추종 기록에 영향을 주지 않습니다.
- 기존 팀 설정과 같은 이미지·설정을 사용하고 자동 저장합니다. cosmetic은 옆 탭에서 계속 편집할 수 있습니다.
- 검증: Windows 빌드, 태그 부착/회전 및 cosmetic 기하 검사 통과. 실제 Skin editor의 태그 탭과 머리 부착 미리보기의 켜기/끄기 반영을 확인하고 기존 표시 상태로 복원했습니다.


## 0.20 태그 / cosmetic 이미지 목록

- **Skin editor → 태그 / cosmetic → 이미지 추가**로 PNG/JPG/BMP를 추가합니다. 원본을 내부 이미지로 복사하므로 원본 파일을 옮겨도 사용할 수 있습니다. 새 항목이 목록에 추가되며 기존 이미지를 덮어쓰지 않습니다.
- **태그 선택 / cosmetic 선택** 창에서 이미지와 이름을 보고 고릅니다. 선택하면 아래에서 이름·크기·연결 줄 길이 또는 앞뒤 위치·회전을 조절합니다. 선택, 표시 여부, 아이템별 조절값은 종료 후에도 유지합니다. 각 목록은 예시를 포함해 최대 64개입니다.
- 새 예시는 태그 10종(루비 하트, 초승달, 황금 별, 푸른 불꽃, 에메랄드 잎, 얼음 결정, 보라 보석, 네잎클로버, 태양 문양, 은빛 깃털)과 cosmetic 10종(검은 날개, 천사 날개, 박쥐 날개, 황금 왕관, 붉은 뿔, 얼음 뿔, 은빛 사슴뿔, 월계관, 네온 지느러미, 불꽃 날개)입니다.
- 기존 개인 이미지와 조절값은 **기존 이미지** 항목으로 이관합니다. 이전 파일은 보존하며 새 목록은 실행 파일 옆 `personal-tag-library.json`, `personal-cosmetic-library.json`, 추가 이미지 파일은 `personal-*-item-번호.rgba`에 저장합니다.
- 이미지 추가·교체와 목록 미리보기 준비는 메뉴에서만 처리합니다. 실제 게임에는 선택한 두 이미지의 기존 그리기 경로를 사용합니다. 목록 미리보기는 64×64로 보관해 20개 기준 픽셀 데이터 약 320KiB, 두 목록을 모두 채워도 약 2MiB입니다(그래픽 드라이버의 별도 할당 비용 제외). 실제 FPS 차이는 측정하지 않았습니다.
- 20개 예시 원본은 `app/res/personal/library/`에 있습니다. 내장 imagegen 도구로 각각 생성했으며 전체 요청문은 같은 폴더의 `ASSET-PROMPTS.json`에 보관했습니다.
- 검증: 전체 자동 검사와 Windows 빌드 통과. 실제 화면에서 태그/cosmetic 목록, 선택 후 머리 부착 미리보기, 추가 파일의 새 항목 등록과 실제 종료·재실행 후 이미지/크기 복원을 확인했습니다. 검사 후 기존 선택과 조절값으로 복원했습니다. 저장·복원, 한글/따옴표 이름, 아이템별 값 분리, 목록 상한, 손상 목록 덮어쓰기 방지를 자동 검사했습니다.


## 0.21 자기 몸을 따라 가두리 유지

- 자기 몸을 따라 한 바퀴 돌고 있는 상태에서 기존 BOT 키를 켜면, 머리 근처에서 같은 방향으로 이어지는 자기 몸의 한 바퀴 경로를 찾아 따라갑니다. 순간 회전량으로 추정한 원보다 실제 몸의 경로를 우선하므로 타원형 가두리도 유지합니다. 켜는 순간 잠깐 직진 중이어도 완성된 몸 경로가 있으면 인식합니다.
- 처음 잡은 한 바퀴 모양을 유지하며, 안전한 동안 먹이를 따라 밖으로 빠져나가지 않습니다. 상대 머리·몸·경기장 경계가 위험하면 기존 수비 회피를 우선하고, 안전해지면 경로 추종을 다시 시도합니다. 사망하지 않는다는 보장은 아닙니다.
- 몸에 아직 한 바퀴가 없거나 머리가 기존 몸에서 멀리 떨어져 있으면 기존 회전 유지/수비 판단으로 돌아갑니다. BOT을 끄거나 죽으면 잡아둔 경로를 해제합니다. 새 전략 창이나 단축키는 추가하지 않았습니다.
- 몸 경로 수집은 BOT 활성화 시에만 최대 4,096점으로 제한하며, 이후에는 128점 경로를 최대 30Hz로 추종합니다. BOT을 끈 일반 플레이에서는 몸 경로 수집·추종·충돌 예측을 실행하지 않습니다. 활성화 시 수집 비용도 BOT 성능 기록에 포함합니다.
- 검증: 전체 자동 검사 통과. 타원형 4개 시작 위치 × 양방향, 각각 48초 모의 주행에서 경로 유지 확인. 실제 봇 입력을 연결한 양방향 40초 모의 주행, 직진 구간 활성화, 사망/재시작 초기화, 미완성·직선·반대 방향·손상 경로 거부와 장애물 회피 검사도 통과했습니다. 512개 장애물과 128점 경로의 안전한 추종 검사에서 판단당 평균 약 0.036ms(200회)를 기록했습니다. 실서버 생존률이나 FPS 향상 수치는 아닙니다.


## 0.22 태그의 부드러운 흔들림

- **Skin editor → 태그 → 부드러운 흔들림**에서 켜고 끕니다. 팀 설정의 이미지 태그 항목에도 같은 스위치가 있습니다. 태그별로 저장되며 재실행 후 유지합니다. 기존 태그에는 처음 한 번 켜진 상태로 적용하고, 끄면 이전의 움직임으로 돌아갑니다.
- 켜면 줄 끝과 태그가 연결점을 중심으로 조금씩 따로 움직이고, 방향 전환 시 관성으로 흔들린 뒤 서서히 가라앉습니다. 직진/스킨 미리보기에서도 작은 흔들림이 보입니다. 이미지의 연결점은 줄 끝에 계속 붙어 있습니다.
- 프레임마다 고정된 양의 각도 계산만 추가하며 이미지 업로드나 파일 읽기는 하지 않습니다. 사망·긴 일시 중지·태그 교체 시 이전 흔들림 상태를 초기화합니다. 스킨 미리보기와 게임은 별도 상태를 사용합니다.
- 검증: 연결점 유지, 직진 시 흔들림, 60/120FPS 동작 일치, 각도 경계와 과도한 흔들림 제한, 일시 중지/재생성 초기화, 이전 설정 읽기, 아이템별 켜짐/꺼짐 저장 자동 검사 통과. 실제 스킨 설정에서 스위치 표시와 켜기/끄기 반영, 선택한 태그의 저장 값을 확인했습니다.


## 0.23 반복 계산 축소와 끊김 원인 기록

- 이름과 점수의 표시 폭을 지렁이별로 재사용합니다. 닉네임, 글꼴, 실제 글꼴 크기가 바뀌면 갱신하고, 점수는 화면에 표시되는 문자열이 달라질 때만 폭을 다시 계산합니다. 자기 이름이나 꺼진 점수 표시의 불필요한 작업도 생략합니다. 외곽선과 이름/점수의 기존 배치는 유지합니다.
- NTL 팀원 목록을 수신할 때 서버별 식별자 조회표(8KiB)를 만듭니다. 이름 색과 타겟 표시에서 매번 최대 128명 목록을 두 번 훑던 작업을 조회표 한 번 확인으로 줄입니다. 팀 연결, 같은 서버, 10초 유효기간 검사는 계속 수행합니다.
- 미니맵의 부드러운 변화 계산과 픽셀 변환을 한 번의 순회로 합쳤습니다. 다양한 크기/보간값에서 기존 부동소수점 값과 출력 픽셀이 동일함을 검사했습니다. 팀 위치 표시 및 맵 모양은 유지합니다.
- 성능 기록에 `commands_ms`, `queue_submit_ms`, `present_ms`를 추가했습니다. 각각 그리기 준비, Vulkan 명령 제출 호출, 화면 표시 요청 호출의 CPU 경과 시간입니다. GPU 자체의 실행 시간을 측정한 값은 아닙니다. `worst_*`에는 각 1초 구간에서 가장 길었던 프레임의 단계별 시간을 보관합니다. `playing_frames`는 게임 화면 프레임 수이며 `worst_playing`으로 최장 프레임이 게임 화면인지 구분합니다.
- 기존 CSV 열 순서는 유지하고 새 열을 끝에 추가했습니다. 제출 시간은 준비/큐/표시 시간을 포함하며, 프레임 대기에도 네트워크 처리가 포함됩니다. 중첩되는 값을 합산해 전체 프레임 시간으로 해석하면 안 됩니다. 파일 기록은 기존 별도 스레드에서 수행합니다.
- 검증: 전체 자동 검사 및 Windows 빌드 통과. 이름/점수가 그대로인 600프레임은 첫 2회의 폭 측정만 수행했습니다(기존 1,200회). 팀 조회는 모든 65,536개 식별자에 대해 기존 결과와 비교하고 서버 별칭, 목록 삭제, 범위 밖 식별자를 검사했습니다. 로그는 평균과 최장 프레임 구분, 다음 구간 초기화, 게임/메뉴 구분을 검사했습니다.
- CPU 미니맵 비교(각 방식 2,400회, 순서 교대, 동일 PC): 다른 빌드 작업 종료 후 256×256은 약 0.0261→0.0251ms, 512×512는 약 0.1008→0.0993ms였습니다. 빌드와 동시 실행한 검사에서는 약 10% 차이가 났지만 부하의 영향을 받으므로 대표 향상률로 사용하지 않습니다. 실제 게임 전체 FPS/입력 지연의 개선 수치는 아직 측정하지 않았습니다.
- 실제 0.23 실행 파일에서 게임 접속, 미니맵 표시, 사망 장면 정지와 메뉴 복귀를 확인했습니다. 성능 CSV의 35개 열 및 게임/메뉴 구분 기록도 확인했습니다. 실팀 연결 상태의 이름 색은 이번 실행에서 별도로 확인하지 않았으며 조회 결과 동일성은 자동 검사로 검증했습니다.
- 화면 표시 대기 방식, 봇의 판단 전략, 몸통 렌더링 방식은 이번에 변경하지 않았습니다. 표시 방식은 새 로그에서 병목이 확인되면 후속 검토합니다.


## 0.24 메뉴의 고양이 밈

- 사용자가 제공한 `slp-cat-knock.gif`를 원본 그대로 포함했습니다. 메인 메뉴 중앙의 점수/플레이 시간 위에서 반복 재생하며 입력란과 버튼을 가리지 않습니다. 창이 작으면 원래 비율을 유지하면서 줄입니다.
- 300×188, 4프레임, 프레임당 200ms의 원래 속도로 재생합니다. 시작할 때 한 번만 해독·업로드하고 메뉴에서는 준비된 프레임만 선택합니다. 프레임의 RGBA 픽셀 데이터는 약 0.86MiB이며 게임 중에는 이 애니메이션의 갱신이나 그리기를 실행하지 않습니다.
- 검증: Windows 빌드 통과. 실제 메뉴에서 GIF 프레임 변화, 비율과 배치, 입력란/버튼과 겹치지 않는 것을 확인했습니다. 제공한 원본과 포함된 GIF의 해시도 동일합니다.


## 0.25 메뉴 밈의 투명 배경과 오른쪽 아래 배치

- 고양이 밈을 메인 메뉴 오른쪽 아래로 옮겼습니다. 화면 가장자리와 24 UI 단위의 간격을 두며 작은 창에서는 크기를 줄입니다.
- 원본 GIF에는 이미 투명한 배경이 있었지만 클라이언트의 GIF 해독 과정에서 흰 테두리가 나타났습니다. 원본의 네 프레임을 RGBA PNG로 미리 풀어 읽도록 바꿔 투명도를 보존합니다. 그림을 새로 생성하거나 다시 그리지 않았습니다.
- 각 PNG는 원본 GIF의 해당 프레임과 픽셀·알파 값이 동일하고, 원래의 200ms 간격과 네 프레임 반복 재생을 유지합니다. 실행 중 반복 해독/업로드는 없고 게임 중에도 표시하지 않습니다.
- 검증: 네 프레임의 원본 RGBA 일치와 프레임 간격 확인, Windows 빌드 통과. 실제 메뉴 오른쪽 아래에서 흰 테두리 없이 움직이는 모습과 중앙 메뉴를 가리지 않는 것을 확인했습니다.


## 0.26 현재 몸을 따라 가두리 유지

- NTL 공식 안내의 가두리 동작을 참고해, 직접 만든 원/타원에서 머리와 꼬리를 3~4마디 이상 겹친 뒤 **T 두 번**으로 켜는 사용법에 맞췄습니다. NTL의 내부 코드를 복제하거나 모든 봇 모드를 동일하게 만든 것은 아닙니다. 참고: https://ntl-slither.com/slither/
- 켤 때의 경로를 계속 고정하는 대신, 활성화 중 최대 10Hz로 현재 자기 몸에서 한 바퀴 경로를 다시 찾습니다. 회전 방향을 유지하며 일시적으로 몸 정보가 없거나 잘못됐으면 마지막 정상 경로를 보존합니다. 한 번에 경로 길이가 25% 이상 달라지는 후보는 버립니다.
- 현재 몸 길이와 한 바퀴 길이를 비교해 겹치는 여유를 조절합니다. 최소 4개 몸 표본과 몸 두께, 지연에 따른 여유를 확보합니다. 겹침이 많으면 몸의 바깥쪽으로 조금씩 넓히고, 부족하면 안쪽으로 보정합니다. 한 번의 보정 폭을 몸 반지름의 바깥 35%/안쪽 50%로 제한합니다.
- 바깥쪽에 상대가 가까우면 확대를 멈추고 현재 몸 경로를 우선합니다. 해당 경로가 위험하면 안쪽 경로를 확인하고, 그것도 위험하면 기존 수비 회피를 적용합니다. 가두리 유지 중에는 먹이 탐색과 자동 부스트를 하지 않습니다.
- 새 UI나 단축키는 추가하지 않았습니다. BOT이 꺼져 있으면 몸 경로 수집/탐색은 실행하지 않습니다. 사망·재생성·시계 초기화 때 이전 경로를 해제합니다. 경로 갱신은 최대 4,096점, 추종은 128점과 기존 최대 30Hz 판단 주기로 제한하며 비용은 BOT 성능 기록에 포함합니다.
- 실제 봇 입력을 연결한 모의 주행에서 원/타원 × 양방향 × 촘촘한/성긴 몸 표본의 8개 조건에서 각각 80초 동안 움직인 몸을 갱신했습니다. 몸 길이 15% 성장 후 5% 감소, 실제 조향 적용 지연 80/160ms 교대, 일시적인 몸 정보 누락을 함께 검사했습니다. 여덟 경우 모두 각각 667회 확인 중 667회 폐곡선이 유지됐고 마지막 겹침 길이는 약 61~116 게임 좌표 단위였습니다. 이 결과는 실서버 생존율이나 NTL과 동일한 성능을 보장하는 수치가 아닙니다.
- 검증: 전체 자동 검사 및 Windows 빌드 통과. 외부 위협이 가까울 때 확대 중단, 안전한 몸 경로 우선, 안쪽 경로/기존 회피 전환과 기존 봇 조작·비활성/사망 상태 검사를 통과했습니다. 실서버에서 장시간 가두리 생존을 비교 측정한 것은 아닙니다.

## 0.29 팀원 현황 UI

- 이 클라이언트도 기존 NTL 요청의 dt에 로컬 성능 표시와 같은 FPS 평균 및 게임 통신 핑을 담습니다. 메뉴에서는 핑을 보내지 않습니다. 현재 서버까지 별도 핑을 재서 팀원의 핑으로 표시하지 않습니다. 값이 없거나 형식/범위가 잘못되면 —로 표시하고, 팀 응답이 10초 넘게 끊기면 FPS·핑을 감춥니다. 수신 시간이 각 팀원의 개별 측정 시간을 보장하지는 않습니다.
- 기존 4초 팀 갱신을 사용합니다. 별도 서버·태그 공유·추가 폴링을 도입하지 않았습니다. 이름 정리와 서버 집계는 팀 응답 변경 시에만 처리하며 최대 128명을 표시합니다.
- 검증: 전체 자동 검사 및 Windows 빌드 통과. NTL 상태 문자열/HTML 공백/누락/잘못된 값/범위, 메뉴·게임 상태 전송, 같은 서버 별칭/인원 집계/빈 목록 및 표시 설정의 저장·이전 설정 호환을 확인했습니다. 실제 실행 파일의 오프라인 시험에서 정상 수치·SOS·다른 서버·메뉴 대기 행과 창 배치를 확인했습니다. 실제 팀 계정의 실시간 수신은 이번 검증에서 연결하지 않았습니다.

| 128명 | 약 0.096ms |

이번 짧은 가상 메시지 시험에서 128명 응답 해석은 약 0.4ms/회, 표시 목록 준비는 약 0.06ms/회였습니다. 응답 해석은 백그라운드에서, 표시 목록 준비는 응답 변경 때만 실행됩니다. 긴 채팅 이력이나 처음 보는 글자까지 검증한 결과는 아닙니다. 표에서 보이지 않는 행을 건너뛰는 최적화는 가능하지만, 현재 측정 기준으로 큰 끊김 해결보다 우선할 이유는 적습니다.

BOT은 판단 함수만 재는 기존 시험 외에 실제 `sbot_go` 전체(주변 몸통 순회와 자기 몸 갱신 포함)를 -O2로 컴파일해 별도 시험했습니다. 고정된 가상 장면에서 30회 준비 후 200회 판단, 3회 반복한 평균의 중앙값입니다. 매 호출 40ms씩 게임 시간을 진행하여 판단 생략이 없음을 확인했습니다.

| 가상 장면 | 일반 회피 / 판단 | 자기 몸 가두리 / 판단 |
| --- | ---: | ---: |
| 상대 8마리 × 몸통 점 256개 | 0.404ms | 0.057ms |
| 상대 32마리 × 몸통 점 1,024개 | 0.824ms | 0.554ms |
| 상대 64마리 × 몸통 점 4,096개: 극단적 부하 | 7.984ms | 7.631ms |

마지막 장면의 일반 회피는 경로 판단 약 0.28ms, 나머지 준비 처리 약 7.71ms였습니다. 소스상 주변 몸통 전체를 순회하는 비용이 남아 있습니다. 보관하는 위험물은 512개로 제한되지만 입력 몸통 순회량 자체는 이 제한을 받지 않습니다. 극단적 장면의 회차별 p99 중앙값은 일반 회피 약 8.60ms, 가두리 약 8.25ms로, 목표인 판단 p99 1ms를 모든 부하에서 만족하지는 못합니다. 실제 플레이에서 이런 장면이 발생했다는 뜻은 아닙니다.

BOT OFF는 동일한 부하 장면에서도 경로 판단 호출 0회를 확인했습니다. 이 시험은 CPU 비용과 비활성 분리를 검증하며 실제 생존율이나 움직이는 상대에 대한 안전성 증명은 아닙니다.

### 개선 우선순위

1. **큰 끊김 원인 계측 보완**: 이벤트 처리/창 재생성, UI/폰트, 설정 저장, 이미지 준비, 렌더 세부 구간을 구분하고 빌드 식별자·원시 프레임 분포·누락 기록 수를 남깁니다. 평소 메모리에 제한된 기록만 보관하고 느린 프레임 전후를 백그라운드로 저장하는 방식이 적합합니다. 목표는 100~200ms 끊김의 시간을 설명하고 같은 조건에서 수정 전후를 비교하는 것입니다.
2. **BOT 주변 몸통 순회 축소**: 네트워크 몸통 변경 시 갱신하는 공간 구획/몸통 묶음 경계로 먼 구간을 먼저 제외합니다. 머리의 이동 거리, 내 회전·통신 지연과 충돌 여유를 반영한 보수적 범위를 사용하고 기존 생략 위험 거리 제약을 보존해야 합니다. 단순히 가까운 몇 마리만 보거나 충돌 점을 무작정 줄이는 방식은 피합니다. 전체 순회 결과와 위험 판단을 비교하고 CPU p99와 생존 재현 시험을 함께 통과해야 합니다.
3. **렌더 명령 준비 2.54ms 분해**: 게임 명령과 ImGui 업로드/새 폰트 텍스처/드라이버 호출을 나누고 GPU 시간도 함께 측정합니다. 현재 코드에 매 프레임 ImGui 메모리 map/flush/unmap이 있지만, 이것이 2.54ms의 주원인인지는 아직 측정하지 않았습니다. 확인 전에는 백엔드를 전면 교체하지 않습니다.
4. **설정 저장 지연과 시간 기준 점검**: 설정 변경 시 메인 스레드의 동기 파일 저장이 발생합니다. 저장 시간이 끊김과 겹치면 변경 묶음 저장/백그라운드 저장으로 전환합니다. 게임 시간 초기화와 ImGui 시간의 관계도 별도 점검 대상입니다.

이번 검증에서 전체 Windows 자동 검사와 메뉴 애니메이션 시간 회귀 검사를 실행했습니다. 자세한 수치는 `build/performance-audit/results.json`, 자동 검사 출력은 `build/performance-audit/regression.txt`에 있습니다.

## 0.30 자기 몸 따라가기 강화

- 한 바퀴 경로를 인식할 때 아주 짧은 몸통 점마다 방향을 재지 않고 몸 두께에 맞는 구간을 사용합니다. 작은 좌표 흔들림을 반복적인 역회전으로 오인해 가두리를 놓치던 문제를 줄였습니다. 한 바퀴 이전에 끊긴 데이터는 여전히 폐곡선으로 인정하지 않습니다.
- 꼬리 끝 데이터가 잘못되어도 그 앞에 온전한 한 바퀴가 있으면 그 경로를 사용합니다. 끊어진 부분을 연결하거나 꼬리 겹침 길이에 포함하지 않습니다.
- 원래 경로와 몸통 반지름의 0.5배 안쪽만 확인하던 동작에서, 최대 1·2·3배 안쪽 경로도 순서대로 확인합니다. 각 후보는 상대 몸·머리의 예상 이동·통신 지연·맵 경계를 검사합니다. 평소 경로가 안전하면 추가 후보를 계산하지 않습니다.
- 안전한 안쪽 우회를 유지하다가 원래 경로에 여유가 생기면 복귀합니다. 경계에서 작은 정보 변화마다 두 경로를 번갈아 선택하는 것을 줄이고, 일반 회피로 나가야 하는 상황에도 안전한 후보 중 몸 경로 쪽으로 돌아가는 방향을 선호합니다.
- 짧은 몸 정보 누락에서는 이전 경로를 유지하며, 250ms 넘게 갱신이 안 되면 바깥으로 확대하지 않습니다. 약 1.5초 이상 새 경로를 얻지 못하거나 머리가 경로에서 크게 벗어나면 오래된 경로를 해제하고 다시 인식합니다. 인식한 실제 몸 경로는 수동 회전에서 추정했던 옛 원형 경로보다 우선합니다.
- 검증: 기존 원형/타원형·양방향·촘촘/성긴 몸통 8개 장면에 좌표 흔들림, 최대 800ms 정보 누락, 손상된 먼 꼬리를 넣은 8개 장면을 추가했습니다. 각 80초, 총 16개 시뮬레이션에서 가두리 검출은 10,671/10,672회였으며 회전 유지·몸 성장/축소·80/160ms 조향 지연 조건을 통과했습니다. 변경 전 BOT 소스는 같은 흔들림 장면에서 가두리를 잃어 약 0.3바퀴만 회전했고, 변경 후 해당 장면은 약 11.4바퀴를 유지했습니다. 이는 가상 시험 결과이며 실서버 생존율 비교가 아닙니다.
- 장애물 위치를 바꾼 시험에서 기존의 중심/0.5배 안쪽 경로가 모두 막힌 23개 경우에 더 안쪽의 안전한 몸 경로를 찾았습니다. 58개 경우에서 우회 유지 및 위협 제거 후 복귀를 검사했습니다. 800ms 누락 유지, 오래된 경로 만료, 재인식, 큰 위치 보정, BOT OFF 탐색 0회도 확인했습니다.
- 조작은 기존 **T 두 번** 그대로입니다. 별도 봇 UI나 단축키를 추가하지 않았습니다. 재현 시험은 `tests/body_follow_recovery_test.c`, `tests/sbot_live_loop_test.c`, `tests/sbot_integration_test.c`에 있습니다.
- 전체 Windows 자동 검사 및 2.6-ntl0.30 빌드 통과. 별도 -O2 부하 시험에서 상대 8마리×몸통 점 256개의 가두리는 평균 약 0.054ms/판단, 32마리×1,024개는 약 0.613ms였습니다(3회 평균의 중앙값). BOT OFF 경로 판단은 0회입니다. 극단적인 전체 몸통 순회 병목은 이번 강화의 해결 범위가 아니며, 실서버 생존율은 아직 비교하지 않았습니다. 결과는 `build/body-follow-performance.json`과 `build/body-follow-regression.txt`에 남겼습니다.

## 0.31 한산할 때 가두리 크기 유지와 접근 대응 여유

- 자기 몸의 한 바퀴를 인식할 때 둘레를 기준으로 기억합니다. 주변에 위협이 없으면 이 크기를 유지하도록 조금만 바깥으로 보정합니다. 남는 몸 길이를 모두 써서 계속 확장하는 방식은 사용하지 않습니다. 몸 길이가 늘거나 줄면 기준 둘레도 그 변화에 맞춰 조정하되, 꼬리 겹침 여유를 우선합니다.
- 앞쪽 몸 경로를 바라보며 생기는 안쪽 쏠림을 작은 바깥 보정으로 상쇄하고, 현재 둘레와 기준 둘레 차이로 보정량을 제한합니다. 바깥 보정 상한은 몸통 반지름의 35%입니다. 통신 지연이 클 때는 더 앞쪽 경로를 보아 늦게 도착하는 조향 때문에 좌우로 흔들리는 것을 줄였습니다.
- 상대 머리까지의 거리에서 충돌 여유를 뺀 뒤, 내 속도·상대 속도와 가속 여유, 통신 지연, 판단 간격 여유, 안쪽으로 회전하는 시간을 계산합니다. 이 대응 여유가 부족해지기 전에 바깥 보정을 점차 줄이며 가까우면 0으로 만듭니다. 현재 멀어지는 상대도 돌아오거나 가속할 수 있어 가까이 있으면 보수적으로 판단합니다. 회전이 느린 몸은 더 먼 거리에서 보정을 중단합니다.
- 위협이 사라지면 크기 유지 보정이 자동으로 돌아옵니다. 기존의 1.5초 경로 충돌 예측, 안쪽 우회, 맵 경계, 오래된 몸 정보에서는 바깥 보정 중단 규칙도 유지합니다. 이 계산은 예측 여유이며 돌발적인 서버 지연이나 모든 상대 움직임에 대한 생존 보장은 아닙니다.
- 검증: 적이 없는 원형/타원형·양방향·80/160ms 조향 지연 8개 장면을 각 3분씩 시뮬레이션했습니다. 가두리 검출은 3,600/3,600회, 둘레 변화는 초기 대비 약 -0.75%~+2.89%였고, 둘러싼 면적의 최저값은 초기의 약 99.4%였습니다. 몸 길이 변화·좌표 흔들림·정보 누락을 넣은 기존 16개 장면도 통과했습니다. 접근/가속/방향 전환 가능한 머리, 높은 지연, 느린 회전, 위험물 목록 초과, 적이 사라진 후 재보정을 별도 검사했습니다. 실서버 장시간 생존율 비교는 하지 않았습니다.
- 재현 시험: `tests/sbot_size_hold_test.c`, `tests/body_outward_guard_test.c`. 전체 Windows 자동 검사 출력은 `build/size-hold-regression.txt`에 있습니다. 조작은 기존 **T 두 번**이며 새 UI나 단축키는 없습니다.

## 0.32 한 바퀴 인식 실패 시 자기 몸에 합류

- 완전히 닫힌 한 바퀴를 인식해야만 몸을 따라가던 조건을 보완했습니다. 한 바퀴가 덜 닫혔거나 머리가 경로에서 조금 떨어져 있어도, 앞에 있는 자기 몸 구간을 찾아 같은 진행 방향으로 합류합니다. 방금 지나온 목 부분과 역방향 구간은 합류 대상으로 삼지 않습니다.
- 합류 경로는 실제 몸 좌표로만 구성하고 양 끝을 억지로 이어 붙이지 않습니다. 몸이 끊긴 곳을 건너뛰지 않으며, 경로 끝에서 꼬리 쪽으로 갑자기 되돌아가지 않습니다. 합류가 끝나 온전한 한 바퀴를 인식하면 그 크기를 기준으로 기존 가두리 유지에 들어갑니다. 상대와 맵 경계에 대한 회피 검사도 그대로 적용합니다.
- `tests/sbot_body_join_test.c`는 95%만 닫힌 원에서 시작해 실제 BOT 출력을 지연시킨 뒤 머리와 몸을 함께 이동시킵니다. 몸 크기 1·3·6에 맞는 회전 속도, 양방향, 성긴 몸 좌표, 80/160ms 조향 지연의 12개 장면에서 각각 약 4.9바퀴를 유지했습니다. 합류 처리를 끈 이전 동작은 첫 장면에서 0바퀴로 몸 경로를 놓쳤습니다. 기존 몸 추종·크기 유지·회피·입력 전달 자동 검사도 통과했습니다.
- 실제 사용자 플레이 장면을 재현한 기록은 없으므로 이번 수정이 보고된 모든 실패를 해결했다고 단정하지 않습니다. 조작은 **T 두 번**이며 별도 BOT UI나 단축키를 추가하지 않았습니다.

## 0.33 NTL 채팅 형식·팀 타겟·연결 지연 개선

- 채팅은 NTL 기본 형태에 맞춰 작은 투명 패널, `시:분:초 닉네임 내용`의 이어지는 줄, 붉은 닉네임·청록색 본문·파란 시각, 아래 입력창으로 바꿨습니다. 긴 문장은 전체 너비로 줄바꿈합니다. 창 위치와 크기를 조절해 저장할 수 있고, 연결 설정/팀원 목록/숨기기는 입력창 옆 `…`에 있습니다. Enter 입력/전송, Esc 게임 복귀, F8/HH 표시는 기존대로입니다. 여러 메시지가 전송 대기 중이면 합쳐 보관하고, Enter를 누르면 통신 작업을 깨워 전송합니다. 전송 실패 시 자동 재발송하지 않습니다.
- 타겟의 NTL `tar` 송신·수신을 구현했습니다. 같은 팀·같은 게임 서버에서 NTL 또는 이 클라이언트로 고른 표적을 과녁으로 표시하며, 화면에서 확인한 표적을 기존 팀 갱신 주기로 다시 알립니다. 약 4초 갱신이며 팀 전체 반영에는 상대의 다음 갱신까지 시간이 더 걸릴 수 있습니다. 마지막 목격 후 5분 만료는 [NTL TMS 안내](https://ntl-slither.com/slither/)를 따릅니다. NTL의 스킨·게임 ID·몸 무늬 식별 형식과 선택적인 링 번호를 유지하고, 로컬 렌더링에서 바뀐 스킨 번호나 잘린 무늬 길이를 전송하지 않습니다. 게임이 제공하는 생명별 serial이 있으면 재사용된 ID를 구분합니다. NTL의 기본 식별 방식 자체가 완전한 전역 고유 ID는 아니므로 serial 없는 서버에서는 동일한 ID/스킨 재사용의 한계가 남습니다.
- Delete는 내 표시와 재전송을 해제하는 동작입니다. NTL 프로토콜에 없는 팀 전체 강제 삭제 명령은 보내지 않습니다. 다른 팀원이 계속 목격하는 표적은 다시 수신될 수 있습니다. 태그 공유는 추가하지 않았습니다. 실제 팀 계정에 시험 메시지를 전송하지 않았으며, 공개 NTL 9.68 배포본의 형식을 확인한 후 독립적으로 구현했습니다. 상대 NTL 화면에서의 실시간 수신은 추가 확인이 필요합니다.

### 핑 조사 결과와 조치

- 기존 `dist/performance.csv`에서 65ms 이상이 연속한 약 89초 구간의 중앙값은 78.2ms였습니다. 또 다른 73개 연속 1초 표본의 중앙값은 78.6ms였습니다. 전체 기록에서 프레임 간격은 약 16.67ms, 네트워크 CPU 처리 평균은 약 0.2ms입니다. 사용자는 같은 주소로 재접속하면 40ms대로 돌아온다고 확인했습니다. 연결별 차이가 있다는 증거지만 이전 로그에는 연결 ID와 TCP RTT가 없어 특정 원인을 확정할 수 없습니다.
- 기존 소켓에도 TCP_NODELAY가 이미 적용되어 있었습니다. 추가로 게임 소켓을 연결할 때마다 Windows의 수신 확인 빈도를 1로 요청해 지연 ACK와 상대의 전송 대기가 맞물릴 여지를 줄였습니다(`SIO_TCP_SET_ACK_FREQUENCY`). 메뉴의 별도 서버 핑 연결도 같은 정책을 사용합니다. 이 PC에서 설정이 지원되는 것을 확인했고, 지원하지 않는 시스템은 원래 방식으로 동작합니다. 시스템 전체 레지스트리나 네트워크 어댑터 설정을 변경하지 않습니다. 이 조치는 가능한 연결 지연 원인에 대한 완화이며, 이번 증상의 원인으로 지연 ACK가 확정된 것은 아닙니다.
- 핑 표시를 렌더 프레임의 표본 인덱스에 의존하던 방식에서 응답 수신마다 갱신하도록 고쳤습니다. 초기에는 실제 받은 표본 수로 평균을 내고, 수신 시각도 새로 읽습니다. 화면에는 클라이언트 송신 대기까지 포함한 실제 요청→응답 시간을 계속 표시합니다. 40ms로 보이게 고정하거나 내부 대기를 빼지 않습니다.
- 성능 CSV 끝에 `connection_id`, `tcp_rtt_ms`, `tcp_min_rtt_ms`, `tcp_retrans_bytes`, `ping_send_queue_ms`, `max_poll_gap_ms`, `prompt_ack`를 추가했습니다. 응답마다 [Windows TCP_INFO](https://learn.microsoft.com/en-us/windows/win32/api/mstcpip/ns-mstcpip-tcp_info_v0)를 조회해 연결의 TCP 지연·재전송, 우리 송신 대기, 통신 처리 사이의 최대 간격을 구분합니다. 측정 불가는 -1입니다. 다음 고핑 구간에서 로컬 대기와 연결/서버 쪽 지연을 좁힐 수 있으며 TCP RTT만으로 서버 처리 시간을 정확히 분리할 수는 없습니다.
- 실제 서버의 `/ptc`를 이용한 접속별 비교는 서버가 연결을 닫아 결과를 얻지 못했습니다. 70~100ms 현상이 40ms로 개선됐다는 실서버 비교 수치는 아직 없습니다. 기존 실행 중인 게임을 종료하거나 자동 재접속시키지 않았습니다.

검증: 전체 Windows 자동 검사 통과(`build/team-chat-ping-regression.txt`). 타겟 송수신 형식·잘못된 데이터·스킨 식별·링 번호 보존·serial 재사용/사망/만료, 핑의 매 표본 갱신·80→40 회복·부분 송신·중복 응답·초기화, 실제 소켓 옵션/TCP 통계 조회 및 WebSocket 순서/종료를 검사했습니다. 현재 채팅 함수를 실제 ImGui로 렌더링한 오프라인 화면에서 한글·긴 닉네임·줄바꿈을 확인했습니다(`build/chat-preview/chat-preview.png`). 기존 플레이가 실행 중이므로 새 바이너리는 `dist/SlitherNative-0.33.exe`로 만들었습니다.

## 0.34 채팅 한글 입력기 연결 복구

- llvm-mingw 빌드에서 기본적으로 비활성화되던 ImGui의 Windows IME 연결을 켜고 `imm32`를 연결했습니다. 입력 중인 한글 조합창과 후보창에 채팅 커서 좌표를 전달해, 화면 왼쪽 위 대신 입력 위치에 표시합니다. Windows 입력기 자체를 제거하거나 시스템 설정을 바꾸지 않습니다.
- 기존 Unicode 입력 경로와 맑은 고딕을 그대로 사용합니다. 한글을 UTF-8로 보관하며 기존 Enter 전송·Backspace 삭제 동작을 유지합니다.
- `python tools/test_korean_input.py`는 빌드된 실제 GLFW/ImGui를 사용해 숨겨진 Windows 창에서 한글 `WM_CHAR` 입력, 글리프, 실제 IME 조합창·후보창 좌표, 채팅창 이동, 입력기가 소비한 Enter, 한 글자 삭제, 일반 Enter 전송을 확인합니다. 전체 검사에도 포함했습니다. 사용자 키보드의 실제 한/영 전환과 조합 과정은 자동 검사 범위 밖입니다. 테스트 중 팀 서버에 메시지를 보내지 않습니다.

## 0.35 채팅 글자 확대·복사/붙여넣기·한글 수신 수정

- 채팅 본문과 입력창 글자를 14px에서 18px로 키웠습니다. 줄 간격과 입력창 높이도 맞추고, 다음 한 글자가 줄 끝에 들어가지 않으면 다음 줄로 넘깁니다.
- 입력창의 Ctrl+A/C/X/V를 검증하고 우클릭 전체/선택 복사·잘라내기·붙여넣기·전체 선택 메뉴를 추가했습니다. 받은 메시지도 우클릭하여 본문 또는 닉네임·시각을 포함한 내용을 복사할 수 있습니다. 우클릭으로 여러 줄을 붙여넣으면 한 줄로 정리하며 900바이트 한도에서 한글 중간을 자르지 않습니다.
- 포함된 JSON 라이브러리는 `\uXXXX` 중 한 바이트 값만 지원했습니다. 한글 이스케이프 해석 실패 시 원래 JSON 토큰을 표시하던 경로를 제거하고, NTL 수신 문자열에서 Unicode 이스케이프와 surrogate pair를 UTF-8로 해석합니다. 한글이 긴 `\ud55c…` 형태로 보이던 원인을 수정했습니다. HTML 숫자 문자 참조도 지원하며, 표시 길이 제한으로 한글이 반쪽으로 잘리지 않도록 했습니다.
- `build/chat-text-regression.txt`: 전체 Windows 검사 통과. 실제 채팅 입력 위젯에서 단축키·우클릭 편집 명령·한글 길이 한도·IME 위치·삭제·전송을 검증했습니다. 클립보드 테스트는 사용자 클립보드를 덮어쓰지 않도록 시험용 저장소를 사용합니다. JSON 수신은 한글·보조 평면 문자·잘못된 이스케이프 거부·한 번만 해석·용량 경계를 검사했습니다. 실제 채팅 그리기 코드의 오프라인 렌더링으로 확대된 글자와 입력창 배치도 확인했습니다.

## 0.36 채팅 입력과 게임 단축키 분리

- 채팅은 입력창을 클릭했을 때 시작합니다. Enter/Tab으로 자동 진입하지 않습니다. 입력 중 Enter는 전송, Esc나 입력창 밖 클릭은 입력 종료입니다. 명시적으로 선택한 우클릭 편집 메뉴는 입력창으로 돌아와 실행합니다.
- 이전 Windows IME 연결은 커서 위치만 갱신하고 입력하지 않을 때도 연결을 유지했습니다. 이제 실제 텍스트 입력 중일 때만 창의 IME를 연결합니다. 게임 중에는 한글 입력기가 문자 단축키를 가로채지 않으며, 닉네임·설정 등 다른 텍스트 입력창에서는 한글을 계속 사용할 수 있습니다. 사용자의 입력 컨텍스트를 보관했다가 복구하며 시스템 키보드 언어 설정은 변경하지 않습니다. 참고: [Microsoft ImmAssociateContext](https://learn.microsoft.com/en-us/windows/win32/api/imm/nf-imm-immassociatecontext).
- 실제 채팅 위젯과 Windows IME 컨텍스트를 사용하는 `tools/test_korean_input.py`에서 클릭 전 입력 무시·게임 문자키 전달·클릭으로 진입·외부 클릭/Esc/전송 후 IME 해제·Tab/Enter 자동 재진입 방지·한글 입력·복사/붙여넣기를 검증했습니다. 실제 사용자의 키보드 조합을 조작하거나 실행 중인 게임을 종료하지 않았습니다. 별도 실행 파일은 `dist/SlitherNative-0.36.exe`입니다.

## 0.37 채팅 중 마우스 조향 유지

- 채팅 입력 중 모든 수동 입력 패킷을 막던 조건을 분리했습니다. 채팅 중에는 최신 마우스 방향을 계속 전송하며, 입력창 위에 커서가 있어도 마우스를 따라갑니다. 기존 33ms 조향 전송 간격을 유지합니다.
- 채팅 중 Space·Shift·클릭은 가속으로 처리하지 않습니다. 채팅 진입 시 기존 수동 가속을 즉시 해제하고, 문자 단축키·방향키·확대 입력은 기존처럼 채팅/UI에서 처리합니다. 채팅을 마치면 일반 조작이 복귀합니다. 설정 창 등 다른 UI 조작이나 게임 창의 포커스를 잃었을 때는 수동 조향을 계속 차단합니다. BOT 조향은 기존대로 독립적으로 동작합니다.
- `tests/bot_steering_test.c`는 실제 `input_network()`가 전송하는 데이터를 검사합니다. 채팅 중 마우스 방향 변경, 가속 해제 및 재전송 방지, 조향 전송 간격, 채팅 종료 후 일반 가속, 포커스 상실·다른 UI·닫힌 연결 차단을 확인합니다. 실행 중인 사용자 게임은 종료하지 않습니다.

## 0.38 팀원 닉네임 강조·스킨 독립 얼굴 장식

- 같은 게임 서버의 NTL 팀원 이름에 어두운 배경과 팀 색 테두리·표식을 추가했습니다. 외곽선 옵션을 꺼도 팀원 이름은 선명하게 표시합니다. 점수에는 팀 표식을 붙이지 않습니다. `팀 연결 / 설정 → 이름 색상 → 팀원 닉네임 강조` 또는 `Ctrl+F3`으로 켜고 끕니다. 기본값은 켜짐이며 이름 숨김 설정은 그대로 따릅니다. 이름과 점수는 한글을 지원하는 기존 일반 글꼴로 같은 크기에 표시하고 기존 너비 캐시를 유지합니다.
- `스킨 설정 → 태그 / cosmetic 창 → 얼굴`에서 `웃는 얼굴`, `집게 모양 눈`을 각각 선택합니다. 기본 스킨과 직접 만든 스킨 모두에 적용되며 동시에 켤 수 있습니다. 둘 다 끄면 원래 눈으로 돌아갑니다. 집게는 기존 특수 스킨처럼 길게 튀어나온 눈 형태입니다. 머리 방향·몸 크기·줌을 따라가며 스킨 미리보기에도 표시합니다.
- 장식은 내 지렁이에만 적용되고 내 화면에만 보입니다. 몸 무늬, 서버에 전달하는 스킨 정보, 충돌 판정과 팀 타겟 식별은 변경하지 않습니다. 파일 이미지나 추가 네트워크 통신 없이 고정된 도형으로 그립니다.
- 세 설정은 자동 저장되며 기존 설정 파일도 읽습니다. `build/team-face-regression.txt`에서 전체 Windows 자동 검사를 통과했습니다. 설정 저장·복원과 이전 설정의 기본값을 검사했고, 실제 그리기 코드로 색상·회전·동시 표시 및 팀 이름 배경을 렌더링해 확인했습니다(`build/face-preview/face-preview.png`).

## 0.39 색상 선택 그라데이션 스킨

- `스킨 설정 → 태그 / cosmetic 창 → 그라데이션`에서 켜고 색을 2~4개 선택합니다. 각 색은 색상 선택창이나 HEX 값으로 수정할 수 있습니다. 머리 색부터 중간 색을 거쳐 꼬리 색까지 이어지며, `색 순서 뒤집기`와 색 띠 미리보기를 제공합니다. `Ctrl+F2`로 켜고 끄며 색 개수·선택한 색·사용 여부는 자동 저장됩니다.
- 스킨 미리보기와 플레이 화면 모두에 적용됩니다. 기본/직접 만든 스킨, 세 가지 몸통 그래픽 모드, 웃는 얼굴·집게·태그·cosmetic과 함께 사용할 수 있습니다. 끄면 기존 몸 색상으로 돌아갑니다. 서버로 보내는 몸 무늬는 그대로이고 그라데이션은 내 화면의 내 지렁이에만 보입니다.
- 보이는 부분만이 아니라 전체 몸통 샘플의 머리→꼬리 위치로 색을 계산하므로 화면 가장자리에서 일부가 가려져도 색의 기준은 유지됩니다. 가속 빛도 해당 위치의 그라데이션 색을 사용합니다. 기존 몸통 인스턴스의 색과 흰색/빈 텍스처를 재사용하며 추가 몸통 그리기나 텍스처 업로드를 만들지 않습니다.
- `tests/gradient_skin_test.c`에서 2~4개 색의 경계·중간값, 세 렌더 모드의 실제 인스턴스, 껐을 때 원래 데이터 보존, 위치·투명도 유지, 샘플당 한 번 그리기를 검사합니다. 설정 저장·복원·이전 버전 기본값·잘못된 색/개수 범위도 검사합니다. `build/gradient-preview/gradient-preview.png`에서 실제 색상 설정 UI와 색상 계산/몸통 인스턴스를 사용한 평면 미리보기를 확인했습니다.


## 2.6-ntl0.40 — 원래 얼굴 장식과 몸 합류 보정

## 2.6-ntl0.42 — 끊김 보완: 최소화 멈춤, 느린 경로 재접속, Wi-Fi 지연

2026-10-05 플레이 기록 약 51분(전 프레임이 게임 중인 구간 1,835초, 약 11만 프레임)을 다시 분석했습니다. 33.34ms를 넘긴 프레임은 8개뿐이고 대부분 창을 다시 띄운 직후였습니다. 화면을 그리는 쪽에는 줄일 만한 끊김이 남아 있지 않았고, 체감되는 끊김은 아래 세 가지에서 왔습니다.

- **창을 최소화하면 게임 전체가 멈추던 문제**: 최소화 중에는 메인 루프가 창 이벤트를 기다리며 멈춰 화면뿐 아니라 서버 통신과 조종 전송도 끊겼습니다(기록상 5~43초). 이제 최소화 중에도 초당 약 60회 통신·핑·조종 전송과 게임 상태 갱신을 계속합니다. 그리기만 건너뜁니다. 창이 가려지거나 포커스를 잃은 경우는 원래도 멈추지 않았습니다.

## 2.6-ntl0.57 — 렉 원인 조사와 수정

**PC 기록(performance.csv, 0.54~0.55로 약 70분 플레이) 분석**
- 그리기 자체는 가벼웠습니다: 초당 60프레임 유지, 프레임 계산(geometry 0.17ms, 명령 0.08ms, 제출 0.13ms)과 GPU 대기(0.02~0.07ms) 모두 작고, 33ms 넘는 프레임은 전체 프레임의 0.02%였습니다. 기능 추가 전 기록(10/8, 10/9 00시)과 차이가 없습니다. 안전 벽은 측정되는 부담이 없었습니다.

- 네트워크: 그 서버(141.164.36.225:444 등) 핑은 보통 46ms, 가끔 113~136ms까지 튀었고, 한 세션에서는 TCP 재전송(패킷 손실)이 있었습니다. 이 부분은 클라이언트가 아니라 회선·서버 쪽입니다.

**기능별 부담 (소프트웨어 그래픽에서 같은 장면 비교)**
- 불꽃 스킨이 가장 무거웠습니다: 큰 반투명 빛을 많이 겹쳐 그려 0.53 방식은 GPU 시간 +6~11ms(FPS 50 → 36). 빛과 불꽃 개수를 줄이고 크기를 줄여 **약 +2ms**로 낮췄습니다(소프트웨어 그래픽이라 반복마다 값이 흔들림, 실제 GPU에서는 아직 재지 못함)(빛 8마디에 1개, 불꽃 3마디에 2개). 모양은 유지됩니다.

- 안전 벽·밀착 계산은 측정 오차 수준(프레임당 1μs 미만).

**수정**
- **전체 화면을 테두리 없는 창 방식으로** 바꿨습니다. 화면을 꽉 채우는 것은 같지만, 다른 창이 포커스를 가져가도 게임이 최소화되지 않고 계속 그려집니다. Alt+Tab도 빨라집니다.
- `performance.csv`에 GPU 시간(`gpu_game_ms`, `worst_gpu_game_ms`, 실제 GPU 타임스탬프)과 창 상태(`unfocused_frames`: 다른 창이 포커스일 때 그린 프레임, `minimized_ms`: 최소화돼 있던 시간)를 추가했습니다. 다음에 멈추면 창이 밀려난 것인지, 게임이 멈춘 것인지 바로 구분됩니다.
- 검증: 자동 검사 통과(성능 기록 열, 창 함수 포함), 실제 실행 파일(wine)에서 전체 화면 설정으로 시작해 화면 전체를 채우는 것과 새 기록 열을 확인했습니다. 실제 Windows에서 포커스를 뺏겼을 때의 동작은 직접 확인하지 못했습니다.

## 2.6-ntl0.54 — 안전 벽이 꺼져 있던 문제

- 원인: 0.53에서 안전 벽은 기본이 꺼짐이었고, 켜져 있는지 화면에서 알 수 없었습니다. PC의 설정 파일에 `"safe_wall": false`로 저장돼 있었고, 서버 기록의 벽 사망 4번(16:56)은 모두 꺼진 상태에서 났습니다. 안전 벽 계산 자체는 실제 클라이언트로 다시 시험해도 정상이었습니다(마우스를 바깥/한 방향 고정/2.5초마다 바꿈, 모두 사망 0).
- **기본으로 켜짐**: 설정 파일에 값이 없으면 켜진 상태로 시작합니다. 직접 끈 경우에만 꺼져 있습니다.
- **화면 표시**: 게임 중 화면 아래 가운데에 `안전 벽 ON`(초록) / `안전 벽 OFF`(흐림)가 항상 보이고, 벽을 따라 돌리는 동안은 주황색이 됩니다. 켜고 끌 때 화면 가운데에 `안전 벽 켜짐 / 꺼짐`이 1.5초 나옵니다.
- **단축키 추가**: **S 두 번**. 노트북에서는 F 키가 Fn과 함께 눌러야 하는 경우가 있어 Ctrl+F1이 안 먹을 수 있습니다. Ctrl+F1도 그대로 됩니다.
- **기록**: `performance.csv` 끝에 `safe_wall`(1 켜짐/0 꺼짐), `safe_wall_steers`(그 1초 동안 벽을 따라 돌린 횟수), `wall_gap_min`(머리가 벽에 가장 가까이 간 거리)을 남깁니다. 벽에 죽었을 때 켜져 있었는지, 얼마나 붙었는지 바로 확인할 수 있습니다.
- 검증: 실제 실행 파일(wine)에서 기본 켜짐으로 벽에 붙어 미끄러짐(벽과 약 26 거리 유지) → S 두 번으로 끔 → 20초 동안 벽 사망 5번 → S 두 번으로 켬 → 30초 동안 사망 0번. 기록 열과 화면 표시도 같은 실행에서 확인했습니다.

## 2.6-ntl0.53 — 안전 벽(Safewall)과 불꽃 스킨

**안전 벽 (Safewall, Ctrl+F1)**
- NTL의 Safewall과 같은 기능입니다. 벽 가까이에서 마우스가 맵 밖을 가리키면 벽으로 들어가는 대신 벽을 따라 미끄러지도록 방향을 바꿔 보냅니다. 마우스를 안쪽으로 돌리면 바로 원래대로 움직이고, 벽에서 멀 때는 아무것도 하지 않습니다.
- 계산 방식: 지금 속도와 회전 반경(크기·속도·부스트에 따라 바뀜), 핑을 넣어 "지금 끝까지 꺾으면 그리는 원이 벽 안에 남는가"를 매번 확인합니다. 남지 않는 방향은 벽을 따라가는 가장 가까운 방향으로 바꿉니다. 머리가 이미 벽 쪽을 향해 있으면 지나치게 꺾어 정면으로 벽을 향하는 일이 없도록 지금 가던 쪽으로 미끄러집니다.
- 켜면 벽을 따라 돌리는 동안 머리에서 주황색 짧은 선으로 돌리는 방향을 보여 줍니다. 설정 창 **안전 벽 (Safewall)**에서 켜고 끌 수 있고 **벽과의 간격**(−10~10, 1칸 = 4)으로 거리를 조절합니다. 봇(T)이 켜져 있을 때는 봇이 벽을 피합니다. 단축키 안내(F9)에 켜짐/꺼짐이 나옵니다.
- 검증: 지연 0·40·90·160ms, 작은 지렁이·부스트 중인 중간/큰 지렁이, 마우스 방향 5가지(60가지) 시뮬레이션에서 모두 살아서 벽을 따라 돌았고 같은 조작을 끄면 죽었습니다(`tests/safe_wall_test.c`). 실제 실행 파일(wine)을 벽이 죽이는 서버에서 마우스를 계속 바깥으로 둔 채 돌렸더니 꺼진 상태는 25초에 6번 벽에 죽었고, 켠 상태는 45초 동안 한 번도 죽지 않았습니다(길이 8,000 부스트 중에도 마찬가지). 실제 인터넷 지연에서의 동작은 직접 확인하지 못했습니다.

**불꽃 스킨**
- 몸이 빨강·주황·노랑 불 색으로 머리에서 꼬리 쪽으로 일렁이며 흐르고, 아래로 불빛이 번지고, 옆구리에서 불꽃이 피어올라 뒤로 흩어지며 꺼집니다. 부스트 빛도 불 색이 됩니다.
- 설정 창 **불꽃 스킨** 또는 태그/cosmetic 창의 **불꽃** 탭에서 켜고 **불꽃 크기**(0.2~1.5)를 조절합니다. 그라데이션 스킨보다 우선합니다. 내 화면의 내 지렁이에만 보입니다(다른 사람 화면에는 원래 스킨).
- 불빛은 부스트 빛과 같은 그리기 방식이라 그림 수가 크게 늘지 않습니다(불빛은 3마디에 1개, 불꽃은 2마디에 3개). 소프트웨어 그래픽에서 측정한 차이는 50.6 → 49.0 FPS였습니다.

## 2.6-ntl0.51 — 온라인 주소(이름)로 접속

사설 서버를 `start-online.cmd`로 켜면 `some-words-here.trycloudflare.com` 같은 주소가 나옵니다. 서버 PC가 중계 서버(Cloudflare)에 먼저 연결해 두고 친구는 그 중계 서버로 들어오는 방식이라, 공유기 포트 개방이나 Windows 방화벽 설정 없이 다른 네트워크에서 접속할 수 있습니다.

- 서버 칸에 `IP:포트` 외에 **이름 주소**를 넣을 수 있습니다(최대 67자). `https://이름/`처럼 링크째 붙여 넣어도 이름만 남깁니다. 포트를 안 쓰면 80번입니다.
- 이름은 Windows의 주소 찾기로 바꾸고(최대 2.5초), 중계 서버가 어느 서버인지 알 수 있도록 접속 요청의 `Host`에 이름을 넣습니다. 암호화하지 않은 WebSocket(80번 포트)을 씁니다.
- 최근 서버 목록과 핑 표시도 이름 주소를 그대로 다룹니다.
- 주소 칸이 길어져 `user.dat`의 크기가 1,168 → 1,216바이트로 바뀝니다. 이전 파일은 그대로 읽어 닉네임·스킨·단축키·설정이 유지됩니다. **0.51이 저장한 `user.dat`를 0.50 이하로 다시 열면 설정이 기본값으로 돌아갑니다.**

검증: `tests/server_address_test.c`(주소 정리 규칙, 이름 찾기 성공·실패, Host 교체), `tests/user_settings_file_test.c`(이전 크기 파일 읽기), 최근 서버 검사에 이름 주소 추가. 실제 실행 파일을 Linux의 wine에서 돌려, 이름으로만 응답하는 중계 서버(nginx, 80번 포트)를 거쳐 사설 서버에 접속해 플레이되는 것과, 실제 사용 중인 `user.dat`가 한 바이트도 달라지지 않고 옮겨지는 것을 확인했습니다. **Cloudflare 중계를 거친 실제 접속은 이 작업 환경의 네트워크가 막혀 있어 시험하지 못했습니다.** 서버가 켜질 때마다 같은 경로로 직접 접속해 보고 결과를 창에 적습니다.

## 2.6-ntl0.50 — 늦은 프레임 뒤의 불필요한 대기 제거

2026-10-05~06 플레이 기록(게임 중 24,982초, 약 151만 프레임)을 분석했습니다. 평소에는 60FPS에 고정돼 있고 한 프레임의 CPU 작업은 약 0.6ms(통신 0.24, 이동 계산 0.11, 도형 준비 0.18, 제출 0.15)라 줄일 계산은 남아 있지 않았습니다. 33.34ms를 넘긴 프레임은 229개(0.015%)였고, 그중 108개는 같은 모양이었습니다: 화면 대기(GPU·화면 표시가 늦음)가 17~38ms 걸린 프레임 뒤에 프레임 제한이 한 주기(16.7ms)를 통째로 더 쉬어 37~54ms짜리 프레임이 됐습니다.

- **프레임 제한 수정**: 제 시간을 넘긴 프레임 뒤에는 쉬지 않고 바로 다음 프레임을 시작합니다. 늦은 프레임을 따라잡으려고 프레임 간격을 한 주기보다 좁히지는 않으므로, 화면 앞에 프레임이 더 쌓여 표시 지연이 늘지 않습니다. 제 시간에 끝난 프레임의 동작은 그대로입니다(`app/src/game/frame_pacer.h`).
- **끊김 원인 기록 추가**: `performance.csv`의 `clock` 앞에 `events_ms`(창 메시지·입력 처리에 쓴 시간), `oversleep_ms`(프레임 제한 중 Windows가 요청보다 늦게 깨운 시간)와 그 초의 가장 긴 프레임 값 `worst_events_ms`, `worst_oversleep_ms`를 추가했습니다. 기록에 남은 70~230ms 끊김 39건은 프레임 제한 대기 중이거나 어느 단계에도 잡히지 않은 시간이어서 기존 열로는 원인을 가를 수 없었습니다. **이 끊김은 이번에 고치지 못했고**, 새 열이 쌓이면 창 메시지 쪽인지 Windows가 늦게 깨운 쪽인지 구분할 수 있습니다.
- 하지 않은 것: 몸통 겹쳐 그리기 축소(실제 기록에서 화면 대기 평균이 0.06ms라 GPU가 병목이 아님), 스레드 우선순위 올리기(늦게 깨우는 것이 원인인지 아직 기록이 없음).

검증: `tests/frame_pacer_test.c`(제 시간 프레임의 주기 유지, 늦은 프레임 뒤 즉시 시작, 따라잡기 없음, 긴 멈춤 뒤 몰아 그리지 않음) 추가, 성능 기록 검사에 새 열 추가. 실제 실행 파일을 Linux의 wine + 소프트웨어 Vulkan(lavapipe)에서 사설 서버에 접속시켜 같은 장면에서 이전 방식과 비교했습니다. 한 프레임이 약 24ms 걸리는 무거운 장면: 23.2FPS → 38.0FPS(프레임 간격 44.4ms → 27.3ms). 가끔 주기를 넘기는 가벼운 장면(각 40초, 2회씩): 33ms 초과 35·24개 → 1·2개, 57.3·58.4FPS → 60.3·59.9FPS. 소프트웨어 렌더러는 그리기 시간이 CPU에서 걸리므로 실제 GPU와 수치는 다릅니다. **Intel Iris Xe에서의 효과는 다음 플레이 기록의 `over33`로 확인해야 합니다.**

## 2.6-ntl0.49 — 팀원 닉네임 반짝임

- 팀원 닉네임은 항상 팀 색으로 표시되고, 1초에 두 번쯤 밝아졌다 돌아오며 반짝입니다. 글자 뒤에 팀 색 빛이 깔리고, 이름 상자의 테두리와 왼쪽의 별 모양도 같이 커졌다 작아집니다.
- 전에는 "이름 색 통일"을 켜야만 팀 색이 적용됐지만, 이제 그 설정과 상관없이 적용됩니다.
- "팀원 닉네임 강조"(Ctrl+F3)를 끄면 반짝임과 상자가 모두 꺼집니다. 팀 색은 설정 창의 "팀원 이름 색"에서 바꿉니다.
- 팀원 판별은 기존과 같이 NTL 팀 연결에서 받은 정보를 씁니다. 팀에 연결되어 있지 않으면 표시되지 않습니다.

## 2.6-ntl0.48 — NTL 방식 봇

- 봇(T 두 번)을 NTL 모드의 봇과 같은 방식으로 바꿨습니다. NTL 봇은 공개된 "Slither.io Bot Championship Edition"(j-c-m, MPL-2.0)을 고친 것이며, 그 판단 과정을 한 단계씩 그대로 옮겼습니다. 기존의 수비형 봇은 더 이상 호출되지 않습니다(코드는 남아 있습니다).
- **스마트 봇 켬(기본, B 두 번으로 전환)**: 먹이를 먹으며 자라다가(grow), 길이가 "봇 길이"(기본 2000)에 이르면 한쪽으로 계속 돌아 몸을 말고(tocircle), 머리가 자기 몸에 닿으면 그 뒤로는 자기 몸을 따라 계속 돕니다(circle). 길이가 봇 길이 아래로 줄면 다시 자랍니다.
- **스마트 봇 끔**: 길이와 상관없이 처음부터 자기 몸을 따라 돕니다. 직접 원을 만든 뒤 켜는 가두리 용도입니다. 몸이 곧게 뻗은 상태에서 켜면 따라 돌 고리가 없어 그대로 직진합니다(NTL도 같습니다).
- 자라는 동안에는 16방향으로 주변을 나눠, 앞쪽 원 안에 들어온 몸·머리·벽을 발견하면 반대쪽으로 돌고, 여러 방향이 막히면 가장 넓게 열린 쪽으로 빠져나갑니다. 빠르게 다가오는 머리를 피할 때는 부스터를 씁니다.
- 도는 동안에는 자기 몸 바로 바깥을 따라가며, 다른 지렁이의 몸이나 벽이 지나갈 자리에 들어오면 미리 안쪽으로 붙고, 상대 머리가 가까우면 간격을 좁힙니다.
- 봇이 켜져 있어도 마우스 왼쪽 버튼이나 Space를 누르고 있으면 부스터가 들어갑니다(NTL과 같음).
- 설정 창에 "스마트 봇"과 "봇 길이"(100~50000)를 추가했고 `native-settings.json`에 저장됩니다.
- 검증: NTL 모드의 원본 봇 코드와 옮긴 코드를 무작위 장면 3,800개(76,000프레임)에 각각 돌려 결정(목표 지점·부스터·단계)을 비교했습니다. 3,799개 장면이 일치했고(반올림 차이 1 이내), 1개 장면에서 목표 지점이 3 차이 났습니다.

## 2.6-ntl0.47 — 한글 입력 중 화면 깜빡임

- 한글을 칠 때 화면 전체가 번쩍이던 문제를 고쳤습니다. Windows는 조합 중인 글자(예: `ㅎ` → `하` → `한`)를 별도의 작은 창에 띄우는데, 이 창이 게임 창 위에 나타났다 사라질 때마다 화면이 번쩍였습니다.
- 이제 그 창을 띄우지 않고, 조합 중인 글자를 게임이 직접 입력 위치에 밑줄과 함께 그립니다. 완성된 글자는 이전과 같이 입력창에 들어갑니다.
- 한자 변환 후보 창은 그대로 Windows가 띄웁니다.

## 2.6-ntl0.46 — 이름 밑에 상대 전적

- 전적이 있는 상대는 지렁이 이름 바로 밑에 `내 킬 : 내 데스`가 항상 표시됩니다(킬은 초록, 데스는 빨강). 이름 표시가 꺼져 있으면 같이 숨겨집니다.
- 아직 서로 죽이거나 죽은 적이 없는 상대, 이름이 없는 지렁이에는 표시하지 않습니다.
- W를 누르면 뜨는 전체 표는 그대로입니다.

## 2.6-ntl0.45 — 상대 전적 (W 키)

- 게임 중 **W**를 누르고 있으면 화면 가운데에 상대별 킬·데스가 나옵니다. 손을 떼면 사라집니다. 채팅 입력 중에는 뜨지 않습니다.
- 어느 서버에서든 동작합니다. 서버는 누가 누구를 죽였는지 알려 주지 않으므로, 지렁이가 죽는 순간 그 머리가 누구 몸에 닿아 있었는지로 판단합니다. 내 몸에 닿아 죽었으면 내 킬, 내 머리가 닿아 있던 몸의 주인이 나를 죽인 상대입니다. 서버가 킬 수를 알려 주면 그것으로 한 번 더 맞춰 봅니다.
- 닉네임 기준으로 셉니다. 같은 닉네임을 쓰는 사람은 한 줄로 합쳐지고, 이름이 없는 지렁이는 `(no name)` 한 줄에 모입니다.
- 많이 만난 상대부터 20명까지 보이고, 지금 같은 서버에 있는 상대는 밝게 표시됩니다. 벽이나 화면 밖 원인으로 죽은 횟수는 아래에 따로 나옵니다.
- 기록은 프로그램을 켜 둔 동안만 유지됩니다. 서버를 옮기거나 다시 접속해도 이어지고, 프로그램을 끄면 지워집니다.

## 2.6-ntl0.44 — 접속 불가 대응: 재접속 기본 꺼짐, 종료 이유 기록

2026-10-05 14:10경부터 0.43에서 입장 직후 0.3초 안팎으로 게임이 끝나고 다시 접속하는 일이 반복됐습니다(설정의 즉시 재시작이 켜져 있어 자동으로 반복). 같은 PC의 브라우저에서 같은 서버에 이 클라이언트와 같은 순서·같은 내용(닉네임, 직접 만든 스킨 포함)으로 접속하면 정상적으로 입장해 유지됐으므로 서버·IP 차단·접속 절차 문제는 아니었습니다. 클라이언트 쪽 원인은 기록이 없어 확정하지 못했습니다.

- **느린 경로 재접속을 기본 꺼짐으로 변경** (`팀 연결 / 설정 → 느린 경로면 다시 접속`). 이 기능은 한 번 입장에 연결을 최대 3번 맺는데, 서버는 짧은 시간에 연결이 몰리면 접속을 거부합니다(브라우저 시험에서 8초에 9번째 연결부터 거부 확인). 즉시 재시작과 겹치면 연결 수가 더 늘어납니다. 접속 불가의 원인으로 확인된 것은 아니지만 위험에 비해 이득(약 5번 중 1번, 27ms)이 작아 기본값에서 뺐습니다.
- **종료 이유 기록**: 게임 연결이 끝날 때마다 `session-log.txt`에 시각, 서버, 접속 번호, 입장 여부, 지속 시간, 점수, 이유를 한 줄 남깁니다. 이유는 서버가 닫음 / 서버의 게임 종료 알림(v 값) / 서버가 내 지렁이를 제거 / 사망 장면 정지 / 종료·재시작 키 / 접속 제한 시간 / 소켓 오류 / 잘못된 패킷 길이 / 프로토콜 미지원 / 느린 경로 재접속 중 하나입니다. 512KiB를 넘으면 `session-log.previous.txt`로 넘깁니다.
- **기록 보존**: 게임을 다시 켤 때마다 이전 성능 기록 하나만 남고 그 앞의 것은 지워져, 문제가 생긴 순간의 기록이 재실행 두 번에 사라졌습니다. 이제 밀려나는 기록을 `trace-history/performance-날짜-시각.csv`로 옮겨 최근 40개까지 보관합니다. 각 줄 끝에 `clock`(현지 시각)을 추가했습니다.

검증: 설정 저장·성능 기록 검사에 새 항목과 보관 폴더(40개 한도) 검사를 추가했고, 자동 검사는 이전과 같은 범위가 통과했습니다. **이 버전으로 접속 불가가 해결되는지는 확인하지 못했습니다.** 다시 발생하면 `session-log.txt`의 이유로 원인을 짚을 수 있습니다.
